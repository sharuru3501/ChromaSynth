# 本体内蔵 ESP32 との通信(ケーブルなしのリンク)

**状態: ROM 側は実装済み(`src/clink.asm`、PyBoy でテスト済み)。MCU 側(ESP32 のファームウェア)は未実装。実機では、仮想ボタンが ROM に届くこと(START・A・B・十字キー)と、`gpd` が返ることだけ確認した(§6.6)。下りの符号化は、実機の確認(FPGA が反対向きの十字キーの同時押しを消す)を受けて、2026-11-06 に作り直した(キーボード画面方式、§3)。新しい符号化は実機で未確認。**
根拠と未確認事項は [CHROMATIC_INTERNALS.md](CHROMATIC_INTERNALS.md)。ケーブル+外付けブリッジ方式は [BRIDGE.md](BRIDGE.md)(こちらは変更しない。両方式は共存する)。

## 1. 使う経路と制約
```
 ROM ──(VBlank 中に OCPD へ 4 バイト書く)──► FPGA の OBJ パレット RAM ──(MCU の要求 0xD に応じて gpd として返す)──► MCU
 ROM ◄──($FF00 の読み出し)── FPGA が MCU_buttons を物理ボタンに OR ◄──(MCU が命令 9 で 9bit を書く)── MCU
```
| 制約 | 内容 | 設計への影響 |
|------|------|--------------|
| 上り(ROM→MCU) | MCU に見えるのは `bgpd[2..5]`(BG パレット0の色1・2)と `obpd[10..13]`(OBJ パレット1の色1・2)の8バイト | **OBJ パレット1の4バイトだけを使う**(スプライトの属性は 0 =パレット0なので、見た目に影響しない。BG の4バイトは UI の色なので使わない) |
| 書き込み条件 | CGB モードのとき、PPU がモード3(描画中)でないときだけ反映 | VBlank の先頭で書く(`rLY` が 144〜151 のときだけ) |
| 上りの更新通知 | なし(MCU は要求した時点の値を読むだけ) | 連番で新着を検出。MCU は**フレームの 2 倍以上の頻度**(約 8 ms 以下の間隔)で読む |
| 色の上位バイト | コアは 8 ビットそのまま保持するが、実機で上位 1 ビットが保たれる保証はない | **高いほうのバイト(`obpd[11]`、`obpd[13]`)は 7 ビットしか使わない** |
| 下り(MCU→ROM) | MCU が書けるのは 9 ビット(十字4、A、B、SELECT、START、メニュー)。物理ボタンと OR される。**FPGA は上下・左右の同時押しを消す**(実機のソースで確認)。 | **ROM のキーボード画面でだけ**、ボタンの状態を 4 ビット/フレームのシンボル列として読む(§3)。画面の間は物理ボタンを UI に通さない |
| 速度 | 下り 4 ビット × 30 シンボル/秒(1 シンボル 2 フレーム) = **約 15 B/s**、上りは 1 フレームに 1 メッセージ(最大 3 バイト、約 180 B/s) | ノートには十分。DAW のクロック追従や大量の転送は対象外 |

## 2. 上り(ROM → MCU): スロット
OBJ パレット1の色1・色2(`obpd[10..13]`)を、**リンクが確立している間は毎フレーム**書く。`OCPS = $8A`(自動増加)の後に `OCPD` を 4 回。

| バイト | `obpd` | 使えるビット | 内容 |
|--------|--------|--------------|------|
| B0 | [10] | 8 | MIDI メッセージの1バイト目(ステータス) |
| B1 | [11] | 7 | 2バイト目(データバイト、bit7 = 0) |
| B2 | [12] | 8 | 3バイト目(データバイト) |
| B3 | [13] | 7 | **ヘッダ**: bit 6..5 = `len`(スロット内のメッセージの長さ 0〜3)、bit 4..2 = `seq`、bit 1 = `ack`、bit 0 = `nack` |

- 1スロットに**ちょうど 1 つの MIDI メッセージ**。リアルタイム($F8 など)は 1 バイト。SysEx は送らない。ROM の送信キュー `wTx` から、ステータスバイトの種類で長さを決めて取り出す(`$C0`/`$D0` は 2 バイト、`$F0` 以上は 1 バイト、他は 3 バイト)。
- **スロットは次のメッセージで置き換わるまで、データも `len` もそのまま**。新しいメッセージを積んだフレームだけ `seq` が 1 増える(7 を超えたら 0 に戻る)。MCU は `seq` が変わったときに、そのスロットを新着として取り込む。**`len` を毎フレーム 0 に戻してはいけない**(ESP32 の読み出しが 1 フレーム遅れるとメッセージが消える。最初の実装で見つけて直した)。
- MCU が 8 ms 以下の間隔で読めば、ROM が 1 フレームに 1 メッセージしか積まない限り**取りこぼしは起きない**。`seq` が 2 以上飛んだら取りこぼしとして数える(`SlotReader` がそうしている)。
- `ack`・`nack` は下りの応答(§3)。メッセージがないフレームでも毎フレーム書く。
- **リンクが確立するまで OCPD に触らない**。確立中は、シリアル ISR は `wTx` から取らず、アイドルバイトを返す(ケーブル方式と `wTx` を取り合わないため)。リンクが切れるとケーブル方式に戻る。

## 3. 下り(MCU → ROM): キーボード画面とシンボル列
**キーボード画面(`SCREEN_KBD`)でだけ**、ROM は `$FF00` の状態をデータとして読む。この画面の間は、物理ボタンの処理(START、A、保存など)を UI に通さない。保存(SELECT+A)の事故([CARTRIDGE.md](CARTRIDGE.md) §4.6)が起きない。

**画面の出入り**
- 入る: START の画面切り替え(再生 → 音色 → シーケンサー → **キーボード**)。
- 抜ける: **START と SELECT を同時に約 1 秒(60 フレーム)押し続ける**。再生画面に戻る。MCU は SELECT を決して押さないので、データと取り違えない。抜けた直後、両方を離すまで UI はボタンを無視する(離す前にシーケンサーが動かないように)。
- 画面の間でも、**SELECT 単押し(離したとき)は「次のチャンネル」として効く**(そのチャンネルにキーボードの音が鳴る)。
- 時間切れでは抜けない(Bluetooth が途切れても画面は変わらない)。

**シンボル(1 フレームのボタンの状態)**
| 要素 | 押すもの |
|------|----------|
| フェーズ A | **上**だけ(下は押さない) |
| フェーズ B | **下**だけ(上は押さない) |
| データ 4 ビット | bit3 = 左、bit2 = START、bit1 = B、bit0 = A |
| 決して押さない | SELECT、右 |

- **FPGA は上下・左右の同時押しを消す**ので、フェーズ(上/下)とデータ(左)に反対のペアが出ないように割り当てた(最初の設計は上下・左右の同時押しをマーカーにしていて、実機で成立しないと分かった)。
- **連続するシンボルはフェーズ A と B を交互に使う**。同じフェーズが続くフレームは「同じシンボルがまだ押されている」とみなして無視する。したがって MCU は**各シンボルを 2 フレーム以上**(推奨 3 フレーム)押し続ける。ROM は次に期待するフェーズを覚えている(`wClNextPh`)。MCU は、直近のスロットの `ack`(= ROM が最後に受理したシンボルのフェーズ)の反対のフェーズから始める。シンボルの間に離す必要はない(フェーズが変わるだけ)。
- **パケット**: 最初のシンボルの bit3 が種別(0 = 演奏、1 = 汎用)。チェックはどちらも**「4 ビット値の合計 mod 15」**(& 15 ではなく mod 15。bit が 1 つ変わると、重み 1・2・4・8 のどれでも必ず値が変わるため)。
  - **演奏パケット(4 シンボル)**: オン/オフ 1、ノート 7、ベロシティ 3、チェック 4。単音で、ROM が選択中のチャンネルに鳴らす。
    - `s0` = 0, on, note[6:5]; `s1` = note[4:1]; `s2` = note[0], vel(3); `s3` = (`s0 & 7` + `s1` + `s2`) mod 15。
    - ベロシティは MIDI の 0〜127 を `>> 4` して 3 ビットにする(ROM が `(v << 4) | 8` に戻す)。
    - ノートオフは、そのチャンネルが今鳴らしているノートと**同じときだけ**止める(単音のレガートで、新しい音を止めない)。ノートオフは、ノートオンを送ったチャンネルに届く(選択が途中で変わっても)。
  - **汎用パケット(8 シンボル)**: MIDI の 3 バイト(24 ビット)。`s0` = 1, b0[7:5]; 24 ビットが `s0`〜`s6` に続き(`s1` = b0[4:1]、`s2` = b0[0], b1[7:5]、`s3` = b1[4:1]、`s4` = b1[0], b2[7:5]、`s5` = b2[4:1]、`s6` = b2[0] と 0 が 3 ビット)、`s7` = (`s0 & 7` + `s1` + … + `s6`) mod 15。`s6` の下位 3 ビットが 0 でなければ拒否する。
    - 3 バイトに満たないメッセージは **`$FE` で埋める**(ROM の MIDI 解析は `$FE` を無視する。`0` で埋めるとランニングステータスのデータバイトとして誤解される)。
- **物理ボタンによる破損**: OR なので、ユーザーが A や左を押すとデータのビットが立つ。チェックで検出し、ROM は `nack` を立てて蓄積中のシンボルを捨てる。MCU は `nack` を見たらそのパケットを最初から再送する。`nack` は次のパケットの最初のシンボルを受理したときに消える。**チェックは物理ボタン 1 個の混入を検出する程度で、一般のエラー訂正ではない**。
- **SELECT・右・フェーズなし(上下どちらも押されていない)のフレームはシンボルではない**。パケットの途中で物理 SELECT が押されるとそのシンボルが落ち、パケットは完成しない。**MCU は、`ack` が進まない(または `nack`)ときは 30 フレーム(約 0.5 秒)待ってから再送する**(ROM が蓄積中のシンボルを捨てるのを待つ。待たないと、再送の先頭が古い蓄積の続きになる)。
- **途中で止まったパケット**: 30 フレームシンボルが来なければ、蓄積中のシンボルを捨てる。
- **読み取りの一貫性**: `ReadJoy` は十字とボタンを別々に読む(約 20 µs 離れる)ので、その間に MCU が値を更新すると別の時点のものになる。2 回読んで一致したときだけ採用し、違えば 3 回目を採用する。
- キーボード画面以外では、ボタンは普通に UI に届く。MCU は、ユーザーがキーボード画面にいるときだけ送る(画面は ROM が決め、MCU は今のところ知らない。ROM の画面を上りで知らせる拡張は未実装)。

## 4. リンクの確立
- MCU は起動したら **HELLO**(汎用パケットの `$FE $43 $53`)を送る。`$FE` は ROM の MIDI 解析が無視する。HELLO は MIDI 解析には渡さない。
- ROM は HELLO を受け取ったら**リンク確立**とし、上りスロットの書き込みを始める。**確立前は、演奏パケットも汎用パケットも無視する**(キーボード画面でしか読まない上、HELLO のチェックと `$FE $43 $53` の一致が要る)。
- 確立後、有効なパケット(HELLO を含む)が **250 フレーム(約 4 秒。カウンタが 8 ビットのため)** 来なければ、リンクを解除して OCPD への書き込みを止め、ケーブル方式に戻る。MCU は**2 秒ごとに見張り用のパケット**(ノート 0 のノートオフ。リンクが確立していれば何も起こさず、タイマーだけ戻す。4 シンボル)を送る。HELLO は 8 シンボルで長いので、見張りには使わない。
- **MCU は、ユーザーが明示的に `link on` したときだけ送る**。ROM の画面を MCU は知らないので、キーボード画面以外にいるときにシンボルを送ると、START・A・B などが実際の入力として UI に効いてしまう。
- 画面のステータスへの `LINK` 表示は未実装。

## 5.5 MCU 側の実装(2026-11-06、ビルド確認のみ。**本体には書いていない**)
`chromatic-mcu/`(ModRetro の MCU v4.6 + パッチ。README 参照)。
- **中核**(`chromatic-mcu/src/chlink_proto.c`、純粋な C): 符号化(演奏 4 シンボル、汎用 8 シンボル)、シンボルから FPGA のボタンレジスタの値への変換、スロット(`gpd` の 8 バイト)の解釈。**Python の参照実装(`tools/chromatic_link_ref.py`)と 1962 件のベクトルで一致**(`make check-mcu`、ASan・UBSan 付き)。
- **結合テスト**: 本物の C の符号化器の出力を、PyBoy 上の ROM に押させる(`tools/headless_mcu_proto_test.py`)。HELLO で確立、ノートのオン・オフ(音域 36〜107)、ベロシティ、選択チャンネルへの発音、汎用 MIDI、見張りのパケットで 10 秒つながる、位相の同期(ROM が先行/遅れの両方)が通った。**C の検査を弱める変異(`sum & 7`)を、このテストが検出した。**
- **通信タスク**(`chlink_link.c`): `link on` で、**位相の同期(迷いシンボル 1 つ+0.7 秒待つ)→ HELLO** を送り、以降は 2 秒ごとに見張りのパケットを送る。ノートは `note` コマンド(と、のちの BLE MIDI)がキューに積み、タスクが 1 シンボル 50 ms(約 3 フレーム、`link hold` で変更)で送る。音 1 つは約 200 ms。
- **開ループ**: 上り(ack)は実機で確認できていないので、ack に頼らない。位相は、パケットが偶数シンボルなので、欠けなければ毎回同じ位相から始まる。ずれたら `link sync`(迷いシンボル 1 つ: ROM が期待する位相なら受理、違えば無視されるが、どちらでも以後は同じ位相になる)。
- **危険**: ROM がキーボード画面にいないときに送ると、START・A・B などが実際の入力になる。そのため、**`link on` を打つまで何も送らず**、`link on` の前にユーザーがキーボード画面に入れておく。
- 起動時の自己試験(START を押す、`gpd` の定期表示)は、この版で**やめた**(ROM の画面が起動のたびに変わるため)。
- ビルド: `chromatic-mcu/build.sh`(ESP-IDF v5.3)で 785,632 バイト、警告なし。`factory` の枠(1MB)に約 262 KB の余裕を残して収まる。**書き込みは、`docs/MCU_FLASH_SAFETY.md` の手順とユーザーの確認が要る。**

## 6. 速度と遅延の見積もり(未実測)
| 項目 | 値 |
|------|----|
| 演奏パケット(ノートオン/オフ) | 4 シンボル。1 シンボル 2〜3 フレームの保持なら **135〜200 ms**。ack で次を進める(閉ループ)なら 1 シンボル 1〜2 フレームで **70〜135 ms** |
| 汎用パケット(3 バイトの MIDI) | 8 シンボルで 270〜400 ms |
| 上り(ROM → MCU) | 1 フレームに 1 メッセージ。16.7 ms ごと(最大 60 メッセージ/秒) |

**保持フレーム数が遅延を決める。** ROM は ack(スロットの `ack`)を毎フレーム書くので、MCU は ack が進むのを見て次のシンボルへ進める閉ループにできる(最速で 1 フレーム/シンボル、約 17 ms × 4 = 70 ms)。ただし MCU のポーリング(UART 往復約 1.6 ms)と ROM のフレームのずれで、実際は 1〜2 フレームかかる。ESP32 側の実測で決める。

BLE 自体の遅延(10〜30 ms)が加わるので、**体感の遅延は 80〜200 ms と見ておく**。ベースやパッドは使えるが、速いリードは厳しい。ケーブル方式なら数 ms。

### 短縮の余地(実機で必要と分かってから)
1. 1 フレームに 2 回ジョイパッドを読んで、シンボルを倍にする(ack は VBlank 中にしか書けないので、閉ループは 1 フレーム 1 シンボルのまま。開ループにする)。
2. 演奏パケットのベロシティを減らす(オン/オフ 1 + ノート 7 + 固定ベロシティ + チェック 4 = 3 シンボル)。
3. ノートオフを省く(単音のレガートでは新しいノートオンで足りる。最後の音だけオフが要る)。

## 6.5 実機で確認できたこと(2026-11-06、MCU 0.13.8 / FPGA 18.14)
- **MCU から `gpd` を要求すると、8 バイトが返ってくる**(テトリス実行中、毎回同じ値)。並びは、受信バイト `[0..3]` = `obpd[13],[12],[11],[10]`、`[4..7]` = `bgpd[5],[4],[3],[2]`。**したがって上りのスロット(§2)は、MCU 側では `B0 = [3]`、`B1 = [2]`、`B2 = [1]`、ヘッダ `B3 = [0]` と読む**。
- **本体の ESP32 は、アイドルでライトスリープに入り、その間は何もできない**(CHROMATIC_INTERNALS.md §7)。リンクを使う間はライトスリープを止める必要がある(電池の持ちとの引き換え)。
- **MCU が FPGA に書いた仮想ボタン(`MCU_buttons`)が、ゲームの入力として働く**(テトリスの PAUSE が、仮想 START で解除された。ユーザーの目視)。
- 未確認: ROM が `OCPD` に書いた値が `gpd` に反映されるか(§6.6 で、OBJ パレット1が予想と違う値だった)。

## 6.6 実機で ChromaSynth を動かして分かったこと(2026-11-06、ページ 2 から起動)
- **上り(読み取り)**: `gpd` は `00 00 59 EF 62 0C 7B 79`(何を送っても、3 秒ごとでも不変)。後半 4 バイト `62 0C 7B 79` は、ROM が `InitPalette` で書いた BG パレット(`$7B79`、`$620C`)と**一致**する。パレット RAM の内容が MCU に見えることは確認できた。前半 4 バイト(OBJ パレット 1 の色 1・2 = スロット)は `00 00 59 EF` で、**ROM の予想(初期値 `DF 18 DF 18`、通信後はスロット)と合わない**。原因は未確認(OBJ への書き込みが反映されていない、Chromatic が CGB モードで起動していない、など)。
- **下り(仮想ボタン)**: START、A、B は ROM に届く(START = 画面切り替え、A = ノート入力と発音、B = ノート削除。ユーザーの目視)。十字キー単独は、のちに届くと確認できた(下の項目)。
- **マーカー(上下・左右の同時押し)は成立しない**: FPGA の `emu_system_top.v` は、反対向きの十字キーが同時に押されたとき両方を消す(`DOWN & ~UP`、`UP & ~DOWN`、`LEFT & ~RIGHT`、`RIGHT & ~LEFT`)。ROM は上下・左右の同時押しを決して見ない。**最初の符号化(マーカー方式)は使えず、§3 のキーボード画面方式に作り直した。**
- **十字キー単独も、MCU から届く**(開いて 3〜8 秒の間に、下・上・右・左を 1 秒ずつ長押しして、シーケンス画面のカーソルが動いた。ユーザーの目視)。それ以前の試験で届かなかったように見えたのは、ポートを開くたびの自動 START による画面切り替えと、見ていなかったことによるもので、原因は特定できていない。
- **注意**: シリアルポートを開くたびに本体の ESP32 が再起動し、約 8 秒後に試験用ファームが START を 1 回出す(画面が 1 つ進む)。ボタンの試験は、開いて 12 秒以上待ってから行う。

## 7. 未確認事項
- 実機で ROM から OBJ パレットへ書いた値が `gpd` に見えるか。`gpd` のバイト順(MCU の `bswap64` との関係)。
- Chromatic が CGB モードで ROM を起動するか(ヘッダが CGB 対応)。DMG モードなら OCPD は効かない。
- (解決)上下・左右の同時押しは FPGA が消す。マーカー方式は廃止した(§6.6)。
- MCU のカスタムファームウェアが、純正のメニュー(ボタンの `kTxCmd_PokeButton`)や UART の処理と競合しないこと。
- MCU のポーリング間隔(8 ms 以下)が UART(115200 bps、要求と応答の往復で約 1.6 ms)で成立するか。成立しなければ、フレームごとの要求に落とす(ROM の取りこぼしを避けるため、書き込みを 2 フレームに 1 回にする)。
- 仮想ボタンの更新が、ROM の `$FF00` の 2 回の読み(十字とボタン)の間に起きたときの挙動(ROM は 2 回読みで対処している)。
