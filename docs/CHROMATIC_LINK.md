# 本体内蔵 ESP32 との通信(ケーブルなしのリンク)

**状態: ROM 側は実装済み(`src/clink.asm`、PyBoy でテスト済み)。MCU 側(ESP32 のファームウェア)は未実装。実機では何も確認していない。**
根拠と未確認事項は [CHROMATIC_INTERNALS.md](CHROMATIC_INTERNALS.md)。ケーブル+外付けブリッジ方式は [BRIDGE.md](BRIDGE.md)(こちらは変更しない。両方式は共存する)。

## 1. 使う経路と制約
```
 ROM ──(VBlank 中に OCPD へ 4 バイト書く)──► FPGA の OBJ パレット RAM ──(MCU の要求 0xD に応じて gpd として返す)──► MCU
 ROM ◄──($FF00 の読み出し)── FPGA が MCU_buttons を物理ボタンに OR ◄──(MCU が命令 9 で 9bit を書く)── MCU
```
| 制約 | 内容 | 設計への影響 |
|------|------|--------------|
| 上り(ROM→MCU) | MCU に見えるのは `bgpd[2..5]`(BG パレット0の色1・2)と `obpd[10..13]`(OBJ パレット1の色1・2)の8バイト | **OBJ パレット1の4バイトだけを使う**(スプライトの属性は 0 =パレット0なので、見た目に影響しない。BG の4バイトは UI の色なので使わない) |
| 書き込み条件 | CGB モードのとき、PPU がモード3(描画中)でないときだけ反映 | VBlank の先頭で書く(`rLY` が 144〜151 のときだけ) |
| 上りの更新通知 | なし(MCU は要求した時点の値を読むだけ) | 連番で新着を検出。MCU は**フレームの 2 倍以上の頻度**(約 8 ms 以下の間隔)で読む |
| 色の上位バイト | コアは 8 ビットそのまま保持するが、実機で上位 1 ビットが保たれる保証はない | **高いほうのバイト(`obpd[11]`、`obpd[13]`)は 7 ビットしか使わない** |
| 下り(MCU→ROM) | MCU が書けるのは 9 ビット(十字4、A、B、SELECT、START、メニュー)。物理ボタンと OR される | 5 ビット/フレームのシンボル列にする(§3)。物理ボタンとの混在は**物理的に出ない組み合わせ**で見分ける |
| 速度 | 下り 5 ビット × 60 フレーム = **約 37 B/s**、上りは 1 フレームに 1 メッセージ(最大 3 バイト、約 180 B/s) | ノートと CC には十分。SysEx や大量の転送は対象外 |

## 2. 上り(ROM → MCU): スロット
OBJ パレット1の色1・色2(`obpd[10..13]`)を、**リンクが確立している間は毎フレーム**書く。`OCPS = $8A`(自動増加)の後に `OCPD` を 4 回。

| バイト | `obpd` | 使えるビット | 内容 |
|--------|--------|--------------|------|
| B0 | [10] | 8 | MIDI メッセージの1バイト目(ステータス) |
| B1 | [11] | 7 | 2バイト目(データバイト、bit7 = 0) |
| B2 | [12] | 8 | 3バイト目(データバイト) |
| B3 | [13] | 7 | **ヘッダ**: bit 6..5 = `len`(スロット内のメッセージの長さ 0〜3)、bit 4..2 = `seq`、bit 1 = `ack`、bit 0 = `nack` |

- 1スロットに**ちょうど 1 つの MIDI メッセージ**。リアルタイム($F8 など)は 1 バイト。SysEx は送らない。ROM の送信キュー `wTx` から、ステータスバイトの種類で長さを決めて取り出す(`$C0`/`$D0` は 2 バイト、`$F0` 以上は 1 バイト、他は 3 バイト)。
- **スロットは次のメッセージで置き換わるまで、データも `len` もそのまま**。新しいメッセージを積んだフレームだけ `seq` が 1 増える(7 を超えたら 0 に戻る)。MCU は `seq` が変わったときに、そのスロットを新着として取り込む。**`len` を毎フレーム 0 に戻してはいけない**(ESP32 の読み出しが 1 フレーム遅れるとメッセージが消える。最初の実装で見つけて直した)。
- MCU が 8 ms 以下の間隔で読めば、ROM が 1 フレームに 1 メッセージしか積まない限り**取りこぼしは起きない**。`seq` が 2 以上飛んだら取りこぼしとして数える(`SlotReader` がそうしている)。
- `ack`・`nack` は下りの応答(§3)。メッセージがないフレームでも毎フレーム書く。
- **リンクが確立するまで OCPD に触らない**。確立中は、シリアル ISR は `wTx` から取らず、アイドルバイトを返す(ケーブル方式と `wTx` を取り合わないため)。リンクが切れるとケーブル方式に戻る。

## 3. 下り(MCU → ROM): シンボル列
ROM は毎フレーム `$FF00` を読む。MCU は**物理的に出ない組み合わせ**をマーカーにして、5 ビットのシンボルを送る。

| フェーズ | 押すもの | データ |
|----------|----------|--------|
| A | 上 + 下、さらに**左か右のどちらか一方** | 左 = データ bit4 が 1、右 = 0 |
| B | 左 + 右、さらに**上か下のどちらか一方** | 上 = データ bit4 が 1、下 = 0 |
| 共通 | | START = bit3、SELECT = bit2、B = bit1、A = bit0 |

- 十字キーの上下・左右は同時に押せないので、マーカーは物理ボタンでは出ない(**実機で確認が必要**)。
- 「どちらか一方」の制約は、全部押した状態(上下左右すべて)がフェーズ A と B のどちらか区別できなくなるのを避けるためで、1 ビット分のデータを犠牲にしている(元の設計は 6 ビットだったが、曖昧さが見つかって 5 ビットにした)。
- **連続するシンボルはフェーズ A と B を交互に使う**。同じフェーズが続くフレームは「同じシンボルがまだ押されている」とみなして無視する。したがって MCU は**各シンボルを 2 フレーム以上**(推奨 3 フレーム)押し続ける。フェーズは通番の偶奇で、ROM は次に期待するフェーズを覚えている(`wClNextPh`)。MCU は、直近のスロットの `ack`(= ROM が最後に受理したシンボルのフェーズ)の反対のフェーズから始める。
- **パケット**: 最初のシンボルの bit4 が種別(0 = 演奏、1 = 汎用)。
  - **演奏パケット(3 シンボル)**: オン/オフ 1、ノート 7、ベロシティ 3、チェック 3。単音で、ROM が選択中のチャンネルに鳴らす。
    - `s0` = 0, on, note[6:4]; `s1` = note[3:0], vel[2]; `s2` = vel[1:0], check(3)。check = (`s0` の下位 4 ビット + `s1` + vel[1:0]) & 7。
    - ベロシティは MIDI の 0〜127 を `>> 4` して 3 ビットにする(ROM が `(v << 4) | 8` に戻す)。
    - ノートオフは、そのチャンネルが今鳴らしているノートと**同じときだけ**止める(単音のレガートで、新しい音を止めない)。ノートオフは、ノートオンを送ったチャンネルに届く(選択が途中で変わっても)。
  - **汎用パケット(6 シンボル)**: MIDI の 3 バイト。`s0` = 1, b0[7:4]; `s1` = b0[3:0], b1[7]; `s2` = b1[6:2]; `s3` = b1[1:0], b2[7:5]; `s4` = b2[4:0]; `s5` = check = (`s0` の下位 4 ビット + `s1` + … + `s4`) & 31。
    - 3 バイトに満たないメッセージは **`$FE` で埋める**(ROM の MIDI 解析は `$FE` を無視する。`0` で埋めるとランニングステータスのデータバイトとして誤解される)。
- **物理ボタンによる破損**: OR なので、ユーザーが A を押すとデータの A ビットが立つ。チェックで検出し、ROM は `nack` を立てて蓄積中のシンボルを捨てる。MCU は `nack` を見たらそのパケットを最初から再送する。`nack` は次のパケットの最初のシンボルを受理したときに消える。**チェックは物理ボタン 1 個の混入(1〜2 ビット)を検出する程度で、一般のエラー訂正ではない**。
- **途中で止まったパケット**: 30 フレーム(約 0.5 秒)シンボルが来なければ、蓄積中のシンボルを捨てる。
- **マーカーのフレームでは物理ボタンを無視する**(`wJoy` を 0 にする)。通信中に START や A が押されたことにならない。
- **読み取りの一貫性**: `ReadJoy` は十字とボタンを別々に読む(約 20 µs 離れる)ので、その間に MCU が値を更新すると別の時点のものになる。2 回読んで一致したときだけ採用し、違えば 3 回目を採用する。
- 通信を使っていないとき(マーカーが一度も来ない)は、今までと同じ動作。

## 4. リンクの確立
- MCU は起動したら **HELLO**(汎用パケットの `$FE $43 $53`)を送る。`$FE` は ROM の MIDI 解析が無視する。HELLO は MIDI 解析には渡さない。
- ROM は HELLO を受け取ったら**リンク確立**とし、上りスロットの書き込みを始める。**確立前は、演奏パケットも汎用パケットも無視する**(マーカーは物理的に出ないので、誤検出で確立することはない)。
- 確立後、有効なパケット(HELLO を含む)が **120 フレーム(2 秒)** 来なければ、リンクを解除して OCPD への書き込みを止め、ケーブル方式に戻る。MCU は **HELLO を 1 秒ごとに**送り直す(キープアライブ)。
- 画面のステータスへの `LINK` 表示は未実装。

### テスト(`python3 tools/headless_clink_test.py`、先に `make`)
- 下り: 未確立では何もしない/HELLO で確立/演奏パケット(選択チャンネル、レガート、ベロシティ、ノートオフの追従)/汎用パケット(ノートオン・オフ、`$FE` 埋め、CC123)/物理ボタンの混入で拒否され `nack` が立ち再送で受理/汎用パケットも同様/途中で止まったパケットの破棄/通信のシンボルが UI に届かない(画面もシーケンサーも動かない)/パケットの合間の物理 START は効く。
- 上り: 3・2・1 バイトのメッセージ、メッセージがなければスロットが変わらない、40 メッセージが順序どおり欠けず 1 フレーム 1 つ、`ack` が最後のフェーズに追従する(両方のフェーズ)、書き込みは VBlank の中。
- ISR: 確立中は `wTx` を取らない/タイムアウトでケーブル方式に戻る。
- **わざと壊したコード 10 通りのうち 9 通りを検出した**(演奏/汎用のチェック無効、保持中のシンボルの重複受理、UI へのマスク、ISR がキューを取る、ack なし、スロット長を保たない、タイムアウトなし、ノートオフが新しい音を止める)。**検出できなかった 1 つ: 「VBlank の外でも上りを書く」**。PyBoy はパレット RAM のアクセス制限を再現せず、`ROM` は通常 VBlank の先頭で呼ばれるので、遅れたフレームを作らない限り差が出ない。

**このテストが証明しないこと**: FPGA が仮想ボタンを本当に通すこと、書いたパレットが `gpd` として返ること(CHROMATIC_INTERNALS.md の未確認事項)。実機でしか分からない。

## 6. 速度と遅延の見積もり(未実測)
| 項目 | 値 |
|------|----|
| 演奏パケット(ノートオン/オフ) | 3 シンボル。1 シンボル 2〜3 フレームの保持なら **100〜150 ms**。ack で次を進める(閉ループ)なら 1 シンボル 1〜2 フレームで **50〜100 ms** |
| 汎用パケット(3 バイトの MIDI) | 6 シンボルで 100〜300 ms |
| 上り(ROM → MCU) | 1 フレームに 1 メッセージ。16.7 ms ごと(最大 60 メッセージ/秒) |

**保持フレーム数が遅延を決める。** ROM は ack(スロットの `ack`)を毎フレーム書くので、MCU は ack が進むのを見て次のシンボルへ進める閉ループにできる(最速で 1 フレーム/シンボル、約 17 ms × 3 = 50 ms)。ただし MCU のポーリング(UART 往復約 1.6 ms)と ROM のフレームのずれで、実際は 1〜2 フレームかかる。ESP32 側の実測で決める。

BLE 自体の遅延(10〜30 ms)が加わるので、**体感の遅延は 80〜200 ms と見ておく**。ベースやパッドは使えるが、速いリードは厳しい。ケーブル方式なら数 ms。

### 短縮の余地(実機で必要と分かってから)
1. 1 フレームに 2 回ジョイパッドを読んで、シンボルを倍にする(ack は VBlank 中にしか書けないので、閉ループは 1 フレーム 1 シンボルのまま。開ループにする)。
2. 演奏パケットのベロシティを 1 ビットに減らす(オン/オフ 1 + ノート 7 + 固定ベロシティ + チェック 3 = 2 シンボル)。
3. ノートオフを省く(単音のレガートでは新しいノートオンで足りる。最後の音だけオフが要る)。

## 7. 未確認事項
- 実機で ROM から OBJ パレットへ書いた値が `gpd` に見えるか。`gpd` のバイト順(MCU の `bswap64` との関係)。
- Chromatic が CGB モードで ROM を起動するか(ヘッダが CGB 対応)。DMG モードなら OCPD は効かない。
- 十字キーの上下・左右の同時押しが物理的に出ないこと(マーカーの前提)。FPGA 側で同時押しを禁止していないこと(`top.v` ではデバウンスだけに見えるが、実機で確認が必要)。
- MCU のカスタムファームウェアが、純正のメニュー(ボタンの `kTxCmd_PokeButton`)や UART の処理と競合しないこと。
- MCU のポーリング間隔(8 ms 以下)が UART(115200 bps、要求と応答の往復で約 1.6 ms)で成立するか。成立しなければ、フレームごとの要求に落とす(ROM の取りこぼしを避けるため、書き込みを 2 フレームに 1 回にする)。
- 仮想ボタンの更新が、ROM の `$FF00` の 2 回の読み(十字とボタン)の間に起きたときの挙動(ROM は 2 回読みで対処している)。
