### 3.1 バックアップから読んだ結果
```
nvs       data nvs     0x009000   24K
phy_init  data phy     0x00f000    4K
factory   app  factory 0x010000    1M
```
- **アプリの枠は `factory` の 1 つだけ**(1MB)。`otadata` も OTA の枠もない。0x110000 以降の約 3MB は**全部 0xFF の未使用領域**。
- 純正のアプリは **762 KB**(枠の 74%)。残り約 262 KB。アプリ記述子: 版 `0.13.8`、プロジェクト `mcu_fw`、ビルド日 2026-09-29、ESP-IDF `v5.3`。公開ソース v4.6 の設定と一致する。
- ブートローダは約 30 KB(0x1000〜)。ここは書き換えない。
- **結論**:
  1. 「別の枠に書いて切り替える」は、今のパーティションテーブルではできない(OTA の枠がない)。
  2. **第 1 段階(BLE なしの試験版)**: 262 KB の余裕があるので、`factory` の枠に書く。戻すのは `factory` の枠だけをバックアップから書き戻す(約 1MB、115200 bps で約 1.5 分)。パーティションテーブルは触らない。
  3. **第 2 段階(BLE)**: BLE のスタックは 262 KB には収まらないので、パーティションテーブルに OTA の枠(未使用の 3MB を使う)を足す必要がある。**この変更は別途確認を取る。** 純正の `factory` は残せるので、`otadata` を消せば純正に戻る構成にできる。

### 4.2 実際に起きたこと(2026-11-06)
リハーサルの後、ユーザーの LSDJ で、いくつかの曲ファイルの読み込みが FAIL になった。ユーザーの推測では「LSDJ を起動したまま作業したため」。**確認はできていないが、もっともらしい**: esptool は接続のたびに DTR/RTS で ESP32 をリセットするので、ゲームがカートリッジの SRAM に書いている最中に重なると、セーブが壊れる可能性がある(FPGA とカートリッジは動き続けるため、確率は低いと考えていたが、ゼロではなかった)。MCU のフラッシュと LSDJ の曲データ(カートリッジの SRAM)は別のメモリで、今回の作業では SRAM を読み書きしていない。
- **以後の作業の前に、ゲームを終了し、できればカートリッジを抜いておく**(電源を切ってから抜く。電源が入った状態で抜かない)。カートリッジを抜いた状態でメニューが出るかは未確認。出ない場合は、ゲームを起動せずにメニューにいる状態で作業する。
- カートリッジの曲データのバックアップは別の話(必要なら、MR Updater のセーブのバックアップ機能を使う)。

### 5.3 試験ファームウェア v0 を書いた結果と、USB シリアルの性質(2026-11-06)
- v0 を `0x10000` に **27.6 秒**で書き込み、MD5 検証に合格。読み戻しで**アプリ領域はビルドと完全に一致**。先頭 64KB のうち、ブートローダ・パーティションテーブル・phy_init は**バックアップと完全に一致**、**NVS だけ 99 バイト違った**(`0x9024`〜`0x9398`)。私の書き込みは `0x10000` 以降だけなので、本体が動作中に書く設定領域の更新と考えている(前回の確認と今回の間に本体を使っている)。**以後の「先頭の一致確認」は NVS(`0x9000`〜`0xF000`)を除いて行う。**
- v0 は**起動する**: USB のコンソールに ESP-IDF のブートログと `mcu>` のプロンプトが出る(純正はコンソールが GPIO 35/36 向きで USB には出ない)。ポートを開いて 45 秒聞き続けても、再起動の繰り返しや異常はない。
- **USB シリアルの DTR/RTS は ESP32 のリセットに直結している**(FPGA の `top.v`): `EN = ~RTS`(RTS オンの間 ESP32 はリセットされたまま)、`IO0` は DTR/RTS のどちらかがオンなら Low(次のリセットでダウンロードモード)。Mac でポートを開くと既定で両方オンになるので、**ポートを開く前に DTR=False、RTS=False にする**(pyserial なら `s.dtr=False; s.rts=False` を `open()` の前に)。それでも、開いた瞬間に 1 回リセットが入る(起動ログが先頭から出る)。
- **コンソールの入力(Mac → ESP32)は、今のところ届いていない**: CR / LF / CRLF、DTR オンなど試したが、`chver` や `help` に反応しない。**原因は未確認**(ESP-IDF の REPL 設定は正常、FPGA の配線にも入力を止める記述は見つからなかった)。出力(ESP32 → Mac)は確実に動く。
- → **入力に頼らず、本体が自分で試験を行って結果を出力する v1**(パッチ 0002)を作った(未書き込み)。

### 5.5 v1 の自己試験の結果と v2(2026-11-06)
- v1 を書いた後、ポートを開いて(ESP32 が再起動して)42 秒聞いた。**起動ログと `mcu>` は出たが、自己試験の出力は 1 行も出なかった**(「selftest start」すら出ない)。ユーザーの目視でも、テトリスの PAUSE 画面は変化なし(仮想 START は送られていない)。
- 原因の仮説(**未確認**): 純正のタスクの優先度は FPGA 通信 15・電源管理 16、**コンソール(REPL)は既定の 2、私の試験タスクは 3**。優先度の高いタスクが CPU を使い続けているなら、低いタスクは動けない。コンソールが `mcu>` を 1 回出したあと入力に反応しないことも説明できる。もう 1 つの可能性: `printf` が flush されていない(行バッファの問題)。
- v2(パッチ 0003): 試験タスクを優先度 18、コンソールを 17 にする。出力を標準出力と **ROM の直接出力(`esp_rom_printf`)**の両方に出す。タスク開始直後に「selftest task started」を出す(タスクが動いているかを見分けるため)。
- v2 のイメージ: 783,488 B、ヘッダ・チェックサム・ハッシュは有効。まだ書き込んでいない。

### 5.6 v2 の結果と v3(2026-11-06)
- v2 を書き込み(27.7 秒、MD5 検証合格、アプリ領域は読み戻しで一致、ブートローダ・テーブル・phy_init はバックアップと一致)。ポートを開いて 40 秒聞いた結果: **「selftest task started」は出た(タスクは動く)が、その 6 秒後の出力も、コンソール入力への反応も出ない**。ユーザーの目視でも、テトリスの PAUSE 画面は変化なし。
- **原因(ソースで確認)**: 純正の電源管理 `pwrmgr.c` が、操作がない状態が 100 ms 続くと `esp_light_sleep_start()` で **ライトスリープ(CPU 停止)**に入る。起きるのは FPGA からの UART メッセージ(GPIO10 が Low)のときだけ。眠っている間は、タイマー・タスク・コンソール入力がすべて止まる。起動の約 2 秒後(`PwrMgr_Task` の開始後)に眠るので、v1・v2 の試験もコンソールも止まっていた。**これは「本体内蔵 ESP32 でゲーム中に通信する」設計全体に効く**(MCU が眠っていると、`gpd` を読むことも仮想ボタンを送ることもできない)。
- v3(パッチ 0004): `PwrMgr_TriggerLightSleep()` を何もしない関数にする(呼び出し元は `IdleTimerCB` だけ)。**電池の持ちが悪くなる**(通信を使う間だけ眠らせない、という切り替えは後で入れる)。
- v3 のイメージ: 783,456 B、ヘッダ・チェックサム・ハッシュは有効。まだ書き込んでいない。

### 5.7 v3 の結果(2026-11-06)
- v3 を書き込み(27.7 秒、MD5 検証合格、アプリ領域は読み戻しで一致、ブートローダ・テーブル・phy_init はバックアップと一致)。
- **自己試験が最後まで実行された**: 起動の約 7 秒後に開始 → `T1`(`gpd` 5 回)→ `T2`(仮想 START 150 ms)→ `T3`(`gpd` 5 回)→ 3 秒ごとの `HB`。**ESP32 は眠らずに動き続けた**。書き込み直後に、ポートを開く前の無人の状態でも試験が走っていた(出力が残っていた)。
- **`gpd` はテトリス実行中に毎回 `61 51 30 A8 35 09 41 4B`**(10 回連続 + 定期読み出しで一致)。並び: 受信バイト `[0..3]` = `obpd[13],[12],[11],[10]`、`[4..7]` = `bgpd[5],[4],[3],[2]`。OBJ パレット1の色1 = `0x30A8`・色2 = `0x6151`、BG パレット0の色1 = `0x414B`・色2 = `0x3509`(どれも RGB555 として妥当。テトリスはパレットを書かないので、Chromatic の自動配色)。**設計(CHROMATIC_LINK.md §2)の想定した並びと一致**。
- **確認できたこと**: 上りの経路の MCU 側(要求 → 8 バイトの受信)が実機で動く。**未確認**: ROM が書いた値が `gpd` に反映されるか(ChromaSynth の ROM が必要)、仮想 START がゲームに届くか(ユーザーの目視待ち)。

### 5.8 仮想ボタンとコンソール入力の結果(2026-11-06)
- **仮想 START がゲームに届いた**(ユーザーの目視): テトリスが PAUSE のとき、MCU が FPGA の `MCU_buttons` に `0x01` を 150 ms 書いたら、**PAUSE が消えてゲームが動き出した**。MCU → FPGA → ゲームの入力、の経路が実機で動く。(ポートを開くたびの 1 回だけ START が送られる。書き込み直後の無人の試験とその後の試験で、PAUSE が 2 回切り替わっていたため、最初の確認は見逃されていた。)
- **コンソールの入力が効くようになった**: ライトスリープを止め(v3)、コンソールの優先度を上げた(v2)ことで、`chver`・`help` に返事がある。入力が届かなかった原因は、**MCU がライトスリープで止まっていたこと**だった(DTR/RTS は、ポートを開く前にオフにしていれば問題ない)。
- 以後、`sym <16進>`(FPGA のボタンレジスタ)と `gpd` を対話的に使える。

### 5.15 v9 → v11 → v12(2026-11-07、ユーザーの留守中、「文鎮化だけ避ければ確認なしで進めてよい」との指示のもと)
