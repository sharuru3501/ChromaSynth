# Chromatic の内部構造(ケーブルなしで MIDI を通す経路の調査)

調査日: 2026-11-06。**情報源は ModRetro の公開リポジトリのソース読解のみ**で、実機では何も確認していない。
読んだソースの版: FPGA **v18.14**、MCU **v4.6**(アプリ 0.13.8、ESP-IDF 5.3.0)。**ユーザーの個体と同じ版**(MCU v0.13.8 / FPGA v18.14 / FW v4.6、2026-11-06 に報告)。他の版では挙動が違うかもしれない。
書き込みの安全手順: [MCU_FLASH_SAFETY.md](MCU_FLASH_SAFETY.md)。
(`ModRetro/chromatic_fpga`、`ModRetro/oss-chromatic-console-mcu`。どちらも GPL-3.0。)

## 1. 構成
```
 カート ─► FPGA (Gowin GW5A, GB コア = MiSTer Gameboy_MiSTer) ─► 画面/音/リンクポート
             ▲  │  ボタン、USB(複合デバイス)
   UART      │  ▼  (システム管理用、非同期、低速)
          MCU (ESP32、WiFi/BLE あり、ファームウェア公開、ESP-IDF v5.3)
```
- USB-C は FPGA に繋がり、複合 USB デバイスのシリアル(CDC)が MCU の UART0 に橋渡しされる(115200bps、書き込みとコンソール用)。
- MCU と FPGA の間はもう1本の UART(MCU 側 GPIO9 = TX、GPIO10 = RX)で、パケット(ヘッダ 0x8A/0x8F)を交換する。
- 既存のカスタムファームウェア(ChroMagic、KortaMod、chromatic-recon)は MCU 側だけを置き換える。**FPGA は純正のまま**。

## 2. リンクポートの電気的な手がかり(FPGA ソースより)
- FPGA の端子は `LVCMOS33`(3.3V)。外側との間に**レベルシフタ**があり、`LINK_CLK_DIR_LV` がクロックの向きを制御する(`emu_system_top.v`、`evt1_x2.cst`)。
- したがって**ポート側の電圧は FPGA ではなくレベルシフタの外側の電源で決まり、ソースだけでは分からない**。実測の必要は残る。
- `LINK_SD`(ピン4)は「使っていない、FPGA 側は常に入力」とコメントされている。

## 3. ケーブルなしで ROM と MCU が通信できるか
FPGA 内の GB コアのシリアル(SB/SC)は**外部リンクポートにしか繋がっていない**。MCU の UART には繋がっていない(`emu_system_top.v`)。したがってシリアルでの通信は、FPGA を改造しない限りできない。

ただし**別の経路が2本ある**(どちらも未検証):

| 方向 | 経路 | 根拠 | 見込み |
|------|------|------|--------|
| MCU → ROM | **仮想ボタン**。MCU が UART でアドレス 9 に 9bit を書くと、FPGA が物理ボタンと OR して GB コアの入力に渡す(`top.v` の `BTN_x_filtered \| MCU_buttons[n]`)。MCU 側は `FPGA_Tx_PokeButtons`。 | ソースで確認。ROM は `$FF00` の読みで見える | 1フレームに 8 ビット(十字 4 + A/B/SELECT/START)。**約 60 B/s**。MIDI のノートには足りるが、人間の操作と混ざる。ボタンを押すと誤動作しないよう、通信専用画面かモードが要る |
| ROM → MCU | **パレット読み出し**。MCU がアドレス 0xD で要求すると、FPGA が `gpd`(64bit)を1回だけ返す(`system_monitor.sv`)。`gpd` の正体は §3.1。 | ソースで確認(`video.v:212`) | **1回 8 バイトの上り経路になる**。ROM が CGB パレット RAM に書いたバイトが、そのまま MCU に見える |

### 3.1 `gpd` の中身(ソースで確認)
`video.v` の `assign gpd_out = {bgpd[2], bgpd[3], bgpd[4], bgpd[5], obpd[10], obpd[11], obpd[12], obpd[13]};`

- `bgpd` / `obpd` は **CGB のパレット RAM**(`$FF69` BCPD / `$FF6B` OCPD で ROM が書く 64 バイトずつ)。
- 見えるのは **BG パレット 0 の色1・色2**(`bgpd[2..5]`)と **OBJ パレット 1 の色1・色2**(`obpd[10..13]`)の計 8 バイト。バイトは 8 ビットがそのまま保持される(表示に使うのは上位バイトの下位 7 ビット)ので、**8 ビットの任意データを載せられる**。
- 書き込みは **CGB モードのときだけ**(`isGBC_mode`)、かつ **PPU がモード 3(描画中)でないときだけ**(`vram_cpu_allow = ~mode3`)反映される。ROM は VBlank 中に書く。ChromaSynth はヘッダが CGB 対応(`-c`)なので該当する(Chromatic が CGB モードで起動することは実機で未確認)。
- この `gpd` は「ゲームのデフォルトパレット検出」用で、MCU は純正ではパレットのホットキー処理に使う。
- **副作用**: この4色は画面の色そのもの。通信に使うと、その色を使っている表示が変わる。ROM の UI がこれらの色(BG パレット 0 の色1・2、OBJ パレット 1 の色1・2)を使わないように割り当てる必要がある。
- **同期**: FPGA は要求ごとに現在の値を返すだけで、更新の通知はない。ROM が1バイトを連番(シーケンス)に使い、MCU が連番の変化で新着を検出する形になる。**実効帯域は 7 B × ポーリング回数**。UART は応答が約 1.6 ms なので、60 回/秒なら約 400 B/s が理論上限(実測してから決める)。

どちらも**純正 FPGA のまま、MCU のファームウェアだけで実現できる**。FPGA の改造(Gowin のライセンスと開発環境が必要)は不要。

## 4. 方針
1. **ケーブルあり(A)**: リンクポート+外付け ESP32-S3。設計とテストは済み(BRIDGE.md、FIRMWARE.md)。実測が先。
2. **ケーブルなし(C)**: 本体の ESP32 の BLE MIDI + 仮想ボタン(下り、約 60 B/s)+ パレット読み出し(上り、7 B/回)。**両方向とも理屈の上では成立する**(未実機)。MIDI IN だけなら下りだけで足りる。
3. FPGA 改造(B): 最終手段。

## 5. 未確認事項
- 実機で MCU が仮想ボタンを送ると ROM の `$FF00` に現れるか(遅延、チャタリング除去、メニュー状態との関係)。
- 実機で `gpd` に ROM が書いた値が現れるか、MCU が自前のファームウェアで 0xD を要求して受け取れるか(受信側 `kRxCmd_BGPalette` の扱い)、描画との競合で値が壊れないか、ポーリング間隔の実測。
- ESP32 の BLE と WiFi は**同時に使えない**と chromatic-recon が記している(radio の時分割)。BLE MIDI だけなら問題ない。
- 本体の ESP32 は USB を持たない通常の ESP32 なので、USB-MIDI は使えない(BLE MIDI のみ)。
- MCU ファームウェアを入れ替えるリスク(KortaMod は復元手順と元のバックアップを推奨)。実行前に必ず `esptool.py read_flash` で全体をバックアップする。

## 6. USB シリアルと ESP32 のリセット(FPGA の `top.v` より)
- USB の CDC シリアルは FPGA が持ち、ESP32 の UART0(`ESP32_MCU_D3` = TXD、`D4` = RXD)に繋がる。
- **DTR/RTS が ESP32 のリセットに直結**: `ESP32_EN_INT <= ~UART_RTS`(RTS オンで EN が Low)、`ESP32_IO0_INT <= (DTRRTS == 2'b00)`(DTR か RTS のどちらかがオンで IO0 が Low)。EN は FPGA 内の約 4 ms の遅延を経て ESP32 に届く。
- したがって、**シリアルを開く側(Mac)は DTR/RTS をオフにして開く**こと。オンのまま開くと、開いている間じゅう ESP32 が止まる。
- 2026-11-06 の実機確認: ポートを開く瞬間に 1 回リセットが入る。出力は取れるが、Mac からの入力はコンソールに届かなかった(原因は未確認)。
