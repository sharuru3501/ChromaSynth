# BLE MIDI(本体の ESP32 でワイヤレスに音を鳴らす)の設計

**状態: 実装・ホストテスト・ビルドまで済み(2026-11-06)。本体には書いていない。実機では何も動かしていない。** 実装は §8。
目的: Mac(Ableton Live のコンピュータ MIDI キーボードなど)から Bluetooth MIDI で本体の ESP32 に MIDI ノートを送り、
[CHROMATIC_LINK.md](CHROMATIC_LINK.md) のリンクで ChromaSynth を鳴らす。ケーブルは使わない。

```
Mac (Live / キーボード) ──BLE MIDI──► 本体の ESP32 ──仮想ボタン(キーボード画面)──► ROM ──► 音
                                        ▲                                           │
                                        └────────── gpd(OBJ パレット1のスロット)──────┘
```

## 1. 実現性の測定(ビルドだけ。書き込みなし)
ModRetro の MCU v4.6 を ESP-IDF v5.3 でビルドして、アプリの枠(`factory`、1MB = 1,048,576 B)に BLE が入るかを測った。

| 構成 | 大きさ | 枠の空き |
|------|--------|----------|
| 今の v4(純正の設定のまま = `-Og`、デバッグ向け) | 785,632 B | 約 262 KB |
| `-Os`(サイズ最適化)に変えただけ | 733,568 B | 約 315 KB |
| `-Os` + NimBLE の設定だけ(コードが BLE を呼ばない) | 741,328 B | — (リンクされないので意味がない) |
| **`-Os` + NimBLE(周辺機器のみ・BLE のみ・接続 1)で、最小の BLE MIDI コードを実際に使う** | **1,031,104 B** | **約 17 KB** |

- 純正のビルド設定は**サイズ最適化が切れている**(`CONFIG_COMPILER_OPTIMIZATION_DEBUG`)。`-Os` にするだけで約 52 KB 減る。
- **BLE のスタックとコントローラは約 290 KB。パーティションテーブルを変えなくても枠に収まる。ただし空きは約 17 KB しかない**(この上に MIDI の解析と接続の処理が載る。載せると十数 KB 増える見込み)。
- RAM: BLE を入れると、静的に使える DRAM の領域が 180,736 B から 124,580 B に減り(BT のコントローラが領域を取る)、静的な使用 116,988 B で**残り 7.6 KB**。実行時のヒープの余裕は**測れていない**(実機で測る必要がある)。
- 測定に使った最小コードは、GATT サーバー(MIDI サービス)+ 広告 + 接続パラメータの要求で、ESP-IDF のビルドを通った(警告なし)。**実機では動かしていない。**

### 1.1 方針: パーティションは変えない(A 案)。足りなければ B 案
| 案 | 内容 | 判断 |
|----|------|------|
| **A** | `-Os` + NimBLE の最小構成で、`factory` の枠(1MB)のまま。パーティションテーブルは触らない。書き込みは今までと同じ手順(アプリの枠だけ)。 | **第一候補**。空き 17 KB が薄いので、コードを足して枠を超えたら B 案か下の縮小策へ |
| 縮小策 | LVGL の使わないフォントを外す、アサーションを無音にする、ログ・デバッグ機能を切る、NimBLE のバッファを減らす | A 案の空きが足りなくなったとき。**純正の画面の見た目が変わらないこと**を確かめてから |
| B | パーティションテーブルを書き換え、`factory` を大きく(または OTA の枠を足す)。 | **別途、あなたの確認を取る。** 枠が壊れて起動しなくなるリスクがある |

B 案のリスクについて: ESP32 が起動しなくなっても、USB-C のシリアルは **FPGA が持っていて、DTR/RTS で ESP32 を ROM のダウンロードモードに入れられる**(`CHROMATIC_INTERNALS.md` §6)。したがって ESP32 のファームウェアが壊れていても `esptool` で書き直せる(バックアップ A/B と `restore_stock.sh` がある)。それでも、パーティションテーブルは間違えると全部を書き直す手間が出るので、A 案を先に試す。

### 1.2 `-Os` に変えることの影響
純正と同じソースを、最適化だけ変える。機能は同じはずだが、タイミングが変わる可能性がある(FPGA との UART、ボタン処理、電源管理)。**実機で、純正のメニュー・ボタン・画面・電源が今までどおり動くことを確かめる**(v3・v4 で確認した項目を繰り返す)。

## 2. BLE MIDI の仕様(実装する範囲)
参考: [MIDI over BLE のサービス/特性の UUID とパケットの形式](https://docs.espressif.com/projects/esp-iot-solution/en/latest/bluetooth/ble_midi.html)(Espressif の資料)、[Silicon Labs](https://docs.silabs.com/bluetooth/2.13/bluetooth-code-examples-applications/midi-over-ble)。

- **サービス** UUID: `03B80E5A-EDE8-4B33-A751-6CE34EC4C700`
- **特性(MIDI Data I/O)** UUID: `7772E5DB-3868-4112-A1A9-F2669D106BF3`。性質は **Read、Write Without Response、Notify**。CCCD を持つ。
- **広告**: サービスの UUID を広告のパケットに入れ、名前(`ChromaSynth`)を Scan Response に入れる(31 バイトの制限のため分ける)。
- **接続パラメータ**: 接続間隔 7.5〜15 ms を要求する(遅延 0、監督タイムアウト 4 秒)。Apple は 15 ms 以下を推奨している。
- **パケット**: 1 バイト目 = ヘッダ(`10tttttt`、タイムスタンプ上位 6 ビット)。以降、**各 MIDI メッセージの前にタイムスタンプ下位のバイト(`1ttttttt`)**。ランニングステータスは同じパケットの中だけ。パケットの終わりでランニングステータスは切れる。タイムスタンプは 13 ビット、1 ms 単位。
- **受信側(ChromaSynth)はタイムスタンプを使わない**(来たらすぐ鳴らす。遅延を増やさないため)。

### 2.1 パケットの解析(純粋な C、ホストでテストする)
状態: 「タイムスタンプ待ち」。ヘッダの次から:
1. タイムスタンプ待ちで、bit7 = 1 のバイトが来たら、それはタイムスタンプ。読み飛ばして「ステータス待ち」へ。
2. ステータス待ちで bit7 = 1 のバイトが来たら、ステータス。メッセージを始める(長さはステータスで決まる。`$C0`/`$D0` は 1 データ、他のチャンネルメッセージは 2 データ、`$F8` 以上は 0 データ)。
3. bit7 = 0 のバイト(データ)は、今のメッセージに足す。揃ったらメッセージを渡し、同じステータスのランニングステータスに備えて「タイムスタンプ待ち」へ戻る。
4. タイムスタンプ待ちで bit7 = 0 のバイトが来たら、ランニングステータスのデータ。
5. SysEx(`$F0`〜`$F7`)は読み飛ばす。

テストは、Python で作ったパケット(ランニングステータス、複数メッセージ、タイムスタンプの桁上がり、壊れたパケット、SysEx)を、C の解析器に通して比べる。

### 2.2 MIDI から ROM への対応(第一版)
| MIDI | 動作 |
|------|------|
| ノートオン(ベロシティ > 0) | `ChLinkLink_Note(on, note, vel)`。**MIDI チャンネルは見ない**(オムニ。鳴るチャンネルは ROM で選択中のもの) |
| ノートオフ、ノートオン(ベロシティ 0) | ノートオフ |
| CC123(オールノートオフ)、CC120 | 鳴っている音を止める |
| そのほか | 無視(のちに、`ChLinkLink_Midi` で ROM の MIDI 解析に渡して、プログラムチェンジやピッチベンドに使う) |

## 3. 安全: ROM がキーボード画面にいるときだけ送る(自動で武装する)
問題: MCU のシンボルは、ROM がキーボード画面にいないと、**普通のボタン入力**として UI に効く(START で画面が変わり、A で音符が入る)。いまは `link on` を手で打っているが、ワイヤレスで使うときはコンソールがない。

解決: **ROM が「キーボード画面にいる」ことを、上り(`gpd`)で MCU に知らせる。** 実機で、上りのスロット(OBJ パレット 1)は `gpd` に見えると確認済み。
- ROM は、**キーボード画面にいて、まだリンクが確立していない間**、スロットに**ビーコン**(`len` = 3、B0 = `$F4`、B1・B2 = 0)を書き続ける。
- リンクが確立している間は、今までの通常のスロット(メッセージ、ack)。
- キーボード画面を**出るとき**、ROM はリンクを切り(`wClLinked` = 0)、**終了ビーコン**(`len` = 3、B0 = `$F5`)を 1 回書く。
- MCU は、**パケットを送る直前に必ず `gpd` を 1 回読む**(約 2 ms)。**`$F4` のビーコン、または確立済みのスロット**でなければ送らない。`$F5` を読んだら、リンクを降ろして送るのをやめる。
- BLE の接続があっても、ROM がキーボード画面にいなければ、何も送らない。キーボード画面に入ると、MCU は自動で同期と HELLO を送る。`link on` は、デバッグ用の強制として残す。
- **残るリスク**: 画面を抜けた直後、MCU が最後のパケットを送っている最中(最大 約 200 ms)の数シンボルは、UI に届く可能性がある。その間は、パケットの途中でも各シンボルの前に `gpd` を確認して、さらに短くする(`gpd` の往復は約 2 ms)。

**ROM の変更が要る**(`CLinkUp` と画面の出入り)。ROM とテストを直す。ビーコンの値が、通常のスロットのメッセージと取り違えられないように、MCU 側の解釈とあわせて `chromatic_link_ref.py` に決める。

## 4. 遅延の見積もり
| 段 | 時間 |
|----|------|
| Mac から ESP32 まで(BLE の接続間隔) | 7.5〜15 ms(+ Mac 側のキュー) |
| ESP32 のキュー待ち(前のパケットの送信中) | 0〜約 140 ms(保持 30 ms の場合) |
| 演奏パケット 4 シンボル | 保持 30 ms で約 140 ms、50 ms で 220 ms |
| ROM がボタンを読むまで | 最大 17 ms |
| **合計** | **約 160〜320 ms**(保持 30〜50 ms) |

- 実機で、保持 30 ms まで安定した(20 ms は不安定)ので、**既定を 30〜40 ms にする**。
- **連打の詰まりを避ける**: キューに溜まったノートは、古いものを間引く。単音のレガートなので、**あとから来たノートオンに追い越されたノートオフは送らない**(ROM はノートオフを、今鳴っているノートと同じときだけ効かせる)。キューが長くなったら、鳴らさない音を捨てて、最新の状態に追いつく。
- ack(上り)を使った閉ループ(1 シンボル 1〜2 フレーム)は、必要になったら足す。

## 5. Mac 側の接続
- 本体の ESP32 は、広告で「ChromaSynth」と MIDI サービスの UUID を出す。
- Mac(macOS): **Audio MIDI Setup** → メニュー「ウインドウ」→「MIDI スタジオを表示」→ Bluetooth のアイコン(MIDI デバイス用 Bluetooth 構成)→ **ChromaSynth** の「接続」。接続すると、CoreMIDI の出力先として現れる。(この手順は私が確認していない一般的な方法で、実機でやってみて確かめる。)
- Ableton Live: 設定 → Link, Tempo & MIDI → **MIDI Ports の Output で ChromaSynth の Track を On**。MIDI トラックの出力先を ChromaSynth に向け、コンピュータ MIDI キーボード(Caps Lock の鍵盤アイコン、または `M` キー)で弾く。
- 自動試験用: Mac の Python(`python-rtmidi` など)から、CoreMIDI の出力ポート「ChromaSynth」にノートを送る小さなスクリプトで、Live なしに確かめる。

### 8.1 ビルドの結果(v5)
- **1,033,728 B。`factory` の枠(1,048,576 B)に収まる。空き 14,848 B。** 静的な DRAM の残りは 7,536 B。警告なし。SHA-256 `b73773d7…`。
- 実行時のヒープの余裕は、実機で `heap` を打って確かめる(BLE が起動に失敗しても、`nimble_port_init` の戻り値を見て、残りの機能は動くようにしてある)。
- 空きが約 14.8 KB なので、これ以上コードを足すには、縮小策(§1.1)が要る。
- **書き込みには、`-Os` への変更の影響(§1.2)を確かめる段階を踏む**: まず BLE なしの `-Os` だけを書いて、純正の機能(メニュー、ボタン、画面、電源)に変化がないことを確かめる案を、書き込みの前にあなたと決める。

### 8.2 実機で確認すること(書き込みの後)
1. 純正のメニュー・ボタン・画面・電源が今までどおり動く(`-Os` の影響)。
2. `heap`: BLE 起動後の空きヒープ、最小値。`ble`: 起動できたか。
3. `link stat`: ROM をキーボード画面にしたとき、自動で武装する(`ROM: keyboard screen…` → `armed yes`)。他の画面では武装しない。画面を出ると止まる。
4. Mac から接続(Audio MIDI Setup の Bluetooth 構成)できる。`ble` の `writes`・`MIDI messages` が増える。
5. Mac からのノートで ChromaSynth が鳴る。キーボード画面以外では何も起きない(ビーコンの安全装置)。
6. 遅延の体感、連打、ベロシティ。

### 8.3 実機で確認できたこと(ROM のビーコン、MCU は v4 のまま。2026-11-06)
- **キーボード画面、リンク前**: `gpd` の先頭が `60 00 00 F4`(長さ 3、B0 = `$F4`。ビーコン)。
- **`link on`(HELLO)のあと**: `00 00 00 F4`(長さ 0。普通のスロット。B0 に古い `$F4` が残るが、長さ 0 なのでビーコンに見えない)。
- **START+SELECT の長押しで再生画面に戻ったあと**: `60 00 00 F5`(長さ 3、B0 = `$F5`。終了ビーコン)。何度読んでも同じ(1 回だけ書いたものが保たれる)。
- つまり、**ROM の安全装置の半分(ROM が画面を MCU に伝える)は実機で動いた。** MCU 側の自動武装・送信前の確認(v5)は未確認。

### 8.4 実機で確認できたこと(MCU は `-Os`・BLE なし、2026-11-06)
- **自動で武装する**: ROM をキーボード画面にするだけで、`link on` なしで、約 1.3 秒(同期 + HELLO)で `armed yes`。ド・ミが鳴った(ユーザーの聴感)。
- **ROM の画面を MCU が追う**: 再生画面では送信 0 回(ノートは捨てられ、ROM の画面は変わらない)。キーボード画面に入ると武装し、**出ると即座に武装が解かれ、以後パケットは 1 つも送られない**(中断 0、`dropped` だけが増える)。
- **`-Os` の影響**: 純正のメニュー・ボタン・画面・音は今までどおり(ユーザーの確認)。
- 未確認: BLE(接続、メモリ、遅延)。

### 8.5 実機で、Mac から BLE MIDI で ChromaSynth が鳴った(2026-11-07、MCU v5 + 診断)
- Mac の Audio MIDI Setup → MIDI スタジオ → Bluetooth 構成に、`ChromaSynth` が出て、「接続」できた。CoreMIDI の出力先として `ChromaSynth Bluetooth` が現れた。
- Mac の CoreMIDI から送ったノート(`tools` 外の小さな Swift の送信プログラムで、ド・ミ・ソ、ドレミファソラシド)で、**ChromaSynth が鳴った**(ユーザーの聴感)。ROM はキーボード画面、MCU は自動で武装済み。
- `ble` の診断: `writes 2, MIDI messages 2, note-ons 1`、GATT の読み 3・書き込み 2、購読 6 回(通知 on)、**MTU 256、接続間隔 15 ms**(12 × 1.25 ms)、接続パラメータの要求は成功(rc 0)。最後の書き込みは `BB 9D 80 3C 00`(ヘッダ、タイムスタンプ、ノートオフ)。暗号化(ペアリング)なしで動いた。
- **注意(初回の失敗)**: 最初の接続では、接続の約 15 秒後に MIDI を送った直後に切れ、`writes` が 0 のままだった。原因は特定できていない(接続の直後で購読が済む前だった、MCU の再起動直後だった、など)。診断入りに書き直したあとの接続では、同じ送り方で通った。**再現するか、様子を見る。**
- 未確認: 遅延の体感、速い連打、Ableton Live からの演奏、長時間の安定、ベロシティ、切断・再接続の挙動、MCU の再起動(ポートを開く)後の自動再接続。

### 8.6 遅延の測定と改善(2026-11-07、Live のコンピュータ MIDI キーボードで弾いて、`link lat`)
ユーザーの体感: 保持 40 ms の v5 は「やや遅い」。保持 30 ms で「ちょっと減ったかな」。

MCU の中の、ノートオン 1 つあたり(平均):
| 版 | 待ち時間 | 送信(4 シンボル) | 合計 | `gpd` 1 回 |
|----|----------|------------------|------|-----------|
| v5(保持 40 ms、シンボルごとに直列で確認) | 49 ms | 160 ms | **209 ms**(87 音) | 9.3〜9.9 ms |
| v6(パッチ 0007: 純正の受信タスクが最初の 1 バイトで起きる) | — | — | — | 7.3 ms |
| v7(保持 30 ms + 確認を保持に重ねる) | **51 ms**(最大 252 ms) | **133 ms** | **183 ms**(120 音) | 6.9 ms |

- 状態確認(`gpd`)が約 10 ms かかっていた原因の一部は、純正の受信タスクが、バッファ全体の長さで `uart_read_bytes` を呼び、少しのバイトの応答が 10 ms のタイムアウトまで待たされていたこと(パッチ 0007 で、最初の 1 バイトで起きるように変更)。残りの約 7 ms は FPGA の応答時間(ばらつきが小さく、MCU 側では減らせない)。
- 確認を保持に重ねて(次のシンボルの約 8 ms 前に始める)、送信が 160 → 133 ms。
- **待ち時間は変わらない**: 前のパケット(特にノートオフ。キーを離すたびに 4 シンボル ≈ 133 ms)が終わるのを待つため。ここが、MCU の中で次に大きい。
- 耳に届くまで: MCU の 183 ms + ROM の 1〜2 フレーム(17〜33 ms)+ BLE(接続間隔 15 ms)+ Live/Mac ≈ **230 ms**(体感の見込み。音の出る瞬間は未計測)。
- BLE の到着(Mac → ESP32)は、最短 45 ms 間隔の連打まで問題ない。中断 0。

次の候補(遅延を減らすには、プロトコルの変更が要る): (B) ノートオフを 1 シンボルの「いま鳴っている音を止める」にする → 待ちが約 51 → 15 ms、MCU の合計が約 145 ms。(C) B に加えて、ノートオンを 3 シンボル(ベロシティ 4 段階、検査 2 ビット)にする → 約 115 ms。どちらも、ROM(カード)と MCU の両方の書き込みが要る。

### 8.7 遅延の改善の第 2 段(2026-11-07)。方針: 違う音を絶対に鳴らさない、余裕を持つ、重くしない
ユーザーの希望: 押した音が出る(間違った音より遅延を許容)、動作を重くしない、極限ぎりぎりにしない。
- **採らなかった案**: ノートオンを 3 シンボルにする(ベロシティが 4 段階、検査が 2 ビットになり、違う音が鳴る確率が上がる)。
- **採った案**:
  1. **ノートオフを、検査付きの 2 シンボル(約 70 ms)に**(release)。keep-alive も同じ長さの ping に。組が検査なので、読み違えても、音が早く切れるだけで、違う音にはならない。ROM は最後にノートオンを送ったチャンネルを止める。
  2. **MCU が、鳴っている音を覚え**、違う音のノートオフは送らない。
  3. **保持を 36 ms に**(20 ms は不可、30 ms は可。余裕を約 1.8 倍に)。
  4. **自動回復**: パケットのあと、ROM のスロットの `ack` と `nack` を読み、取られていなければ、位相を揃えて、同じパケットを 1 回だけ再送する。ROM は「途中まで受け取っている」ことも `nack` で知らせる(**確認の穴を、設計中に見つけて塞いだ**: 4 シンボルの途中を読み落とすと、`ack` は一致するのに、パケットは捨てられる)。読み落としで音が失われず、少し遅れて鳴る。
- **見込み**(MCU の中の平均): 待ち時間 約 51 → 約 20 ms、送信 約 157 ms(保持 36 ms)、合計 約 175 ms。耳に届くまで 約 220 ms。遅延は今(約 183 ms)とほぼ同じで、**安定性が大きく上がる**。「ほぼ即時」にはならない。
- **余裕**: ROM の空き 約 2.9 KB(新しい処理は 100 バイト足らず)。MCU のアプリ枠の空き 約 12.6 KB(薄い。足すときは、フォントの縮小などで空きを作る)。
- **テスト**: ROM(PyBoy): release の正常動作、ping、選択チャンネルに依らないこと、無効な組(s0 = 8〜11、s1 = 0〜15 の 90 通りほか)がすべて拒否されること、実際の LEFT の混入が拒否されること、リンク前は無視、読み落としで `nack` が立ち、自動で捨てられること。C の中核: ベクトル 2055 件(release・ack の判定を含む)+ ASan。結合(C の符号化器 → PyBoy の ROM): release・ping・確認の判定・読み落としからの回復の手順。**変異テスト 5 通り**(release の検査なし、選択チャンネルへ release、ping が音を止める、ping がタイマーを戻さない、途中のパケットで `nack` を立てない)を、すべて検出した。
- **互換**: 新しい ROM は、古い MCU の 4 シンボルのノートオフも受け付ける。新しい MCU は、古い ROM では動かない(release が汎用パケットに見える)。**ROM(カード)を先に、MCU を後に書く。**

### 8.8 v8 を書いて、Live で弾いた結果(2026-11-07、330 音、ゆっくり・速く・スタッカート)
- **安定性**: 再送 0、再同期 0、中断 0。**読み落としは一度も起きなかった**(保持 36 ms の余裕が効いた。自動回復は、働く場面がなかった)。BLE は 614 パケットを取りこぼしなく受信(最短 45 ms 間隔まで)。鳴りっぱなしの音なし。キューの間引き 51 件、今の音と違うために送らなかったノートオフ 69 件(重ねて弾いた古い音のオフ)。
- **時間**(MCU の中、ノートオンの平均): 待ち時間 62 ms(最大 663 ms)、送信 163 ms(最初の確認 7 ms + 保持 36 ms × 4 + **パケットのあとの隙間と確認 約 22 ms**)。v7(保持 30 ms、120 音)は、待ち 51 ms、送信 133 ms。
- **音が出るまで**: 待ち時間 + 約 151 ms(最初の確認 + 保持 × 4)。単発なら約 150 ms。パケットのあとの 22 ms は、音ではなく、**次の音の前**に使われる。待ち時間が増えたのは、弾き方が速かった(最大 663 ms は連打でのたまり)ため。**1 音の処理が約 160 ms なので、1 秒に約 6 音を超えると、たまり始める。**
- 判断: 正確さと余裕を優先して、v7 より少し長い。小さい改善の余地(直前の確認から 40 ms 以内なら、最初の確認を省く: 約 7 ms。パケットのあとの隙間 15 ms を縮める)は、効果が約 7〜15 ms で、書き込みの手間に見合うか微妙。

### 8.9 USB-C を抜いて、完全にワイヤレスで鳴った(2026-11-07)
- ChromaSynth がキーボード画面、Mac で BLE 接続済みの状態で、**USB-C を抜いても、Live のキーボードの演奏で ChromaSynth が鳴った**(ユーザーの聴感)。MCU は USB を抜いても再起動せず、BLE の接続も切れなかった。
- つまり、**ケーブルなし(電源は本体の電池)で、Mac → BLE MIDI → 本体 → ROM → 音の全経路が動く**。
- 今の課題(次の作業): ESP32 のライトスリープを切っている(電池)、BLE が常時オン(電池と、ユーザーの懸念)、USB-C の有線(Mac 中継)での演奏、BLE と有線の切り替え。方針: Chromatic の純正メニュー(MENU ボタン)に「MIDI モード(OFF / BLE / USB)」の項目を足し、OFF のときは純正のライトスリープに戻す。有線は、Mac の中継プログラム(CoreMIDI → シリアルのコンソール `note`)。USB-C は FPGA のシリアルで、Chromatic に USB の MIDI キーボードを直接つなぐことはできない。
