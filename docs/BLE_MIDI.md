# BLE MIDI(本体の ESP32 でワイヤレスに音を鳴らす)の設計

> **現状(2026-11-07 時点。この枠だけ読めば足りることが多い)**
> - 本体の ESP32 は **v12**(`chromatic-mcu/patches` 0001〜0009)。OSD の System > MIDI MODE で **OFF / BLE / USB** を切り替える。
> - **BLE**: Mac(Audio MIDI 設定で接続)→ Ableton Live から弾けて、ChromaSynth のキーボード画面で鳴る(USB-C を抜いた完全ワイヤレスでも確認)。**USB**: Mac の中継 `tools/start_usb_bridge.sh`(出力 "ChromaSynth USB")で鳴る。Live は MIDI From = All Ins、MIDI To = ChromaSynth USB。
> - 遅延は耳まで約 200 ms の見込み(シンボルのプロトコルが支配的。BLE と USB でほぼ同じ)。単音のみ。CC などノート以外は MCU が ROM に送っていない。
> - 試験(耳なし、数字で判定)はすべて通過: 265〜1,001 音で再送・再同期・中断 0、BLE の起動・停止で漏れなし、洪水・放置 5 分([log/BLE_MIDI_LOG.md](log/BLE_MIDI_LOG.md) §9.8〜9.10)。
> - 未確認: BLE 接続中の長時間、切断・再接続、ベロシティの聴感、ROM→DAW の上り、電池の持ち。候補: `CHLINK_BLE_TRIM`(−95 KB、Mac での接続確認が要る、[log/BLE_MIDI_LOG.md](log/BLE_MIDI_LOG.md) §9.9)。
>
> 節の案内: 仕様は §2・§3・§9.1〜9.2。§1・§4〜§7・§9.3 は設計時の検討。実装と実機の記録(§8、§9.4〜9.10)は [log/BLE_MIDI_LOG.md](log/BLE_MIDI_LOG.md)。

目的: Mac(Ableton Live のコンピュータ MIDI キーボードなど)から Bluetooth MIDI で本体の ESP32 に MIDI ノートを送り、
[CHROMATIC_LINK.md](CHROMATIC_LINK.md) のリンクで ChromaSynth を鳴らす。ケーブルは使わない。

```
Mac (Live / キーボード) ──BLE MIDI──► 本体の ESP32 ──仮想ボタン(キーボード画面)──► ROM ──► 音
                                        ▲                                           │
                                        └────────── gpd(OBJ パレット1のスロット)──────┘
```

## 1. 実現性の測定(ビルドだけ。書き込みなし)
ModRetro の MCU v4.6 を ESP-IDF v5.3 でビルドして、アプリの枠(`factory`、1MB = 1,048,576 B)に BLE が入るかを測った。

| 構成 | 大きさ | 枠の空き |
|------|--------|----------|
| 今の v4(純正の設定のまま = `-Og`、デバッグ向け) | 785,632 B | 約 262 KB |
| `-Os`(サイズ最適化)に変えただけ | 733,568 B | 約 315 KB |
| `-Os` + NimBLE の設定だけ(コードが BLE を呼ばない) | 741,328 B | — (リンクされないので意味がない) |
| **`-Os` + NimBLE(周辺機器のみ・BLE のみ・接続 1)で、最小の BLE MIDI コードを実際に使う** | **1,031,104 B** | **約 17 KB** |

- 純正のビルド設定は**サイズ最適化が切れている**(`CONFIG_COMPILER_OPTIMIZATION_DEBUG`)。`-Os` にするだけで約 52 KB 減る。
- **BLE のスタックとコントローラは約 290 KB。パーティションテーブルを変えなくても枠に収まる。ただし空きは約 17 KB しかない**(この上に MIDI の解析と接続の処理が載る。載せると十数 KB 増える見込み)。
- RAM: BLE を入れると、静的に使える DRAM の領域が 180,736 B から 124,580 B に減り(BT のコントローラが領域を取る)、静的な使用 116,988 B で**残り 7.6 KB**。実行時のヒープの余裕は**測れていない**(実機で測る必要がある)。
- 測定に使った最小コードは、GATT サーバー(MIDI サービス)+ 広告 + 接続パラメータの要求で、ESP-IDF のビルドを通った(警告なし)。**実機では動かしていない。**

### 1.1 方針: パーティションは変えない(A 案)。足りなければ B 案
| 案 | 内容 | 判断 |
|----|------|------|
| **A** | `-Os` + NimBLE の最小構成で、`factory` の枠(1MB)のまま。パーティションテーブルは触らない。書き込みは今までと同じ手順(アプリの枠だけ)。 | **第一候補**。空き 17 KB が薄いので、コードを足して枠を超えたら B 案か下の縮小策へ |
| 縮小策 | LVGL の使わないフォントを外す、アサーションを無音にする、ログ・デバッグ機能を切る、NimBLE のバッファを減らす | A 案の空きが足りなくなったとき。**純正の画面の見た目が変わらないこと**を確かめてから |
| B | パーティションテーブルを書き換え、`factory` を大きく(または OTA の枠を足す)。 | **別途、あなたの確認を取る。** 枠が壊れて起動しなくなるリスクがある |

B 案のリスクについて: ESP32 が起動しなくなっても、USB-C のシリアルは **FPGA が持っていて、DTR/RTS で ESP32 を ROM のダウンロードモードに入れられる**(`CHROMATIC_INTERNALS.md` §6)。したがって ESP32 のファームウェアが壊れていても `esptool` で書き直せる(バックアップ A/B と `restore_stock.sh` がある)。それでも、パーティションテーブルは間違えると全部を書き直す手間が出るので、A 案を先に試す。

### 1.2 `-Os` に変えることの影響
純正と同じソースを、最適化だけ変える。機能は同じはずだが、タイミングが変わる可能性がある(FPGA との UART、ボタン処理、電源管理)。**実機で、純正のメニュー・ボタン・画面・電源が今までどおり動くことを確かめる**(v3・v4 で確認した項目を繰り返す)。

## 2. BLE MIDI の仕様(実装する範囲)
参考: [MIDI over BLE のサービス/特性の UUID とパケットの形式](https://docs.espressif.com/projects/esp-iot-solution/en/latest/bluetooth/ble_midi.html)(Espressif の資料)、[Silicon Labs](https://docs.silabs.com/bluetooth/2.13/bluetooth-code-examples-applications/midi-over-ble)。

- **サービス** UUID: `03B80E5A-EDE8-4B33-A751-6CE34EC4C700`
- **特性(MIDI Data I/O)** UUID: `7772E5DB-3868-4112-A1A9-F2669D106BF3`。性質は **Read、Write Without Response、Notify**。CCCD を持つ。
- **広告**: サービスの UUID を広告のパケットに入れ、名前(`ChromaSynth`)を Scan Response に入れる(31 バイトの制限のため分ける)。
- **接続パラメータ**: 接続間隔 7.5〜15 ms を要求する(遅延 0、監督タイムアウト 4 秒)。Apple は 15 ms 以下を推奨している。
- **パケット**: 1 バイト目 = ヘッダ(`10tttttt`、タイムスタンプ上位 6 ビット)。以降、**各 MIDI メッセージの前にタイムスタンプ下位のバイト(`1ttttttt`)**。ランニングステータスは同じパケットの中だけ。パケットの終わりでランニングステータスは切れる。タイムスタンプは 13 ビット、1 ms 単位。
- **受信側(ChromaSynth)はタイムスタンプを使わない**(来たらすぐ鳴らす。遅延を増やさないため)。

### 2.1 パケットの解析(純粋な C、ホストでテストする)
状態: 「タイムスタンプ待ち」。ヘッダの次から:
1. タイムスタンプ待ちで、bit7 = 1 のバイトが来たら、それはタイムスタンプ。読み飛ばして「ステータス待ち」へ。
2. ステータス待ちで bit7 = 1 のバイトが来たら、ステータス。メッセージを始める(長さはステータスで決まる。`$C0`/`$D0` は 1 データ、他のチャンネルメッセージは 2 データ、`$F8` 以上は 0 データ)。
3. bit7 = 0 のバイト(データ)は、今のメッセージに足す。揃ったらメッセージを渡し、同じステータスのランニングステータスに備えて「タイムスタンプ待ち」へ戻る。
4. タイムスタンプ待ちで bit7 = 0 のバイトが来たら、ランニングステータスのデータ。
5. SysEx(`$F0`〜`$F7`)は読み飛ばす。

テストは、Python で作ったパケット(ランニングステータス、複数メッセージ、タイムスタンプの桁上がり、壊れたパケット、SysEx)を、C の解析器に通して比べる。

### 2.2 MIDI から ROM への対応(第一版)
| MIDI | 動作 |
|------|------|
| ノートオン(ベロシティ > 0) | `ChLinkLink_Note(on, note, vel)`。**MIDI チャンネルは見ない**(オムニ。鳴るチャンネルは ROM で選択中のもの) |
| ノートオフ、ノートオン(ベロシティ 0) | ノートオフ |
| CC123(オールノートオフ)、CC120 | 鳴っている音を止める |
| そのほか | 無視(のちに、`ChLinkLink_Midi` で ROM の MIDI 解析に渡して、プログラムチェンジやピッチベンドに使う) |

## 3. 安全: ROM がキーボード画面にいるときだけ送る(自動で武装する)
問題: MCU のシンボルは、ROM がキーボード画面にいないと、**普通のボタン入力**として UI に効く(START で画面が変わり、A で音符が入る)。いまは `link on` を手で打っているが、ワイヤレスで使うときはコンソールがない。

解決: **ROM が「キーボード画面にいる」ことを、上り(`gpd`)で MCU に知らせる。** 実機で、上りのスロット(OBJ パレット 1)は `gpd` に見えると確認済み。
- ROM は、**キーボード画面にいて、まだリンクが確立していない間**、スロットに**ビーコン**(`len` = 3、B0 = `$F4`、B1・B2 = 0)を書き続ける。
- リンクが確立している間は、今までの通常のスロット(メッセージ、ack)。
- キーボード画面を**出るとき**、ROM はリンクを切り(`wClLinked` = 0)、**終了ビーコン**(`len` = 3、B0 = `$F5`)を 1 回書く。
- MCU は、**パケットを送る直前に必ず `gpd` を 1 回読む**(約 2 ms)。**`$F4` のビーコン、または確立済みのスロット**でなければ送らない。`$F5` を読んだら、リンクを降ろして送るのをやめる。
- BLE の接続があっても、ROM がキーボード画面にいなければ、何も送らない。キーボード画面に入ると、MCU は自動で同期と HELLO を送る。`link on` は、デバッグ用の強制として残す。
- **残るリスク**: 画面を抜けた直後、MCU が最後のパケットを送っている最中(最大 約 200 ms)の数シンボルは、UI に届く可能性がある。その間は、パケットの途中でも各シンボルの前に `gpd` を確認して、さらに短くする(`gpd` の往復は約 2 ms)。

**ROM の変更が要る**(`CLinkUp` と画面の出入り)。ROM とテストを直す。ビーコンの値が、通常のスロットのメッセージと取り違えられないように、MCU 側の解釈とあわせて `chromatic_link_ref.py` に決める。

## 4. 遅延の見積もり
| 段 | 時間 |
|----|------|
| Mac から ESP32 まで(BLE の接続間隔) | 7.5〜15 ms(+ Mac 側のキュー) |
| ESP32 のキュー待ち(前のパケットの送信中) | 0〜約 140 ms(保持 30 ms の場合) |
| 演奏パケット 4 シンボル | 保持 30 ms で約 140 ms、50 ms で 220 ms |
| ROM がボタンを読むまで | 最大 17 ms |
| **合計** | **約 160〜320 ms**(保持 30〜50 ms) |

- 実機で、保持 30 ms まで安定した(20 ms は不安定)ので、**既定を 30〜40 ms にする**。
- **連打の詰まりを避ける**: キューに溜まったノートは、古いものを間引く。単音のレガートなので、**あとから来たノートオンに追い越されたノートオフは送らない**(ROM はノートオフを、今鳴っているノートと同じときだけ効かせる)。キューが長くなったら、鳴らさない音を捨てて、最新の状態に追いつく。
- ack(上り)を使った閉ループ(1 シンボル 1〜2 フレーム)は、必要になったら足す。

## 5. Mac 側の接続
- 本体の ESP32 は、広告で「ChromaSynth」と MIDI サービスの UUID を出す。
- Mac(macOS): **Audio MIDI Setup** → メニュー「ウインドウ」→「MIDI スタジオを表示」→ Bluetooth のアイコン(MIDI デバイス用 Bluetooth 構成)→ **ChromaSynth** の「接続」。接続すると、CoreMIDI の出力先として現れる。(この手順は私が確認していない一般的な方法で、実機でやってみて確かめる。)
- Ableton Live: 設定 → Link, Tempo & MIDI → **MIDI Ports の Output で ChromaSynth の Track を On**。MIDI トラックの出力先を ChromaSynth に向け、コンピュータ MIDI キーボード(Caps Lock の鍵盤アイコン、または `M` キー)で弾く。
- 自動試験用: Mac の Python(`python-rtmidi` など)から、CoreMIDI の出力ポート「ChromaSynth」にノートを送る小さなスクリプトで、Live なしに確かめる。

## 6. 実装の順序と確認
1. **ホストでテストできる部分**: BLE MIDI パケットの解析器(純粋な C、`chromatic-mcu/src/`)+ Python で作ったパケットとの照合 + ASan。MIDI から `ChLinkLink_Note` への対応表のテスト。
2. **ROM**: ビーコンの出力と画面を出るときの終了ビーコン。PyBoy のテストを足す。
3. **MCU**: ビーコンを見て自動で武装する処理、送信直前の `gpd` 確認、キューの間引き、既定の保持を 40 ms に。
4. **MCU の BLE**: NimBLE のコード(GATT、広告、接続パラメータ)、`-Os` への変更、ビルド設定。**まずビルドして大きさを測る**(枠に収まること)。
5. **実機(書き込みは別途確認)**:
   a. `-Os` だけを書いて、純正のメニュー・ボタン・画面・電源が今までどおり動くことを確かめる(BLE なし)。
   b. BLE を入れた版を書く。ヒープの残量をコンソールに出して確認する。Mac から接続して、ノートを送る。
   c. キーボード画面にいないとき、BLE でノートを送っても何も起きないことを確認する(ビーコンの安全装置)。
6. 保存(SELECT+A)の事故を避けるため、**実機の試験では、SELECT を含む組み合わせを MCU から送らない**(AGENTS.md ルール 20)。

| リスク | 対策 |
|--------|------|
| 枠の空きが約 17 KB しかなく、コードを足すと超える | 縮小策(フォント、アサーション、ログ)。それでも足りなければ B 案(別途確認) |

## 9. MIDI モード(OFF / BLE / USB)と、有線(USB)のための Mac の中継(2026-11-07。v9 以降、本体で動いている)
目的(ユーザーの希望): ESP32 のライトスリープを切りっぱなし、BLE が常時オン、は避けたい(電池と寿命)。BLE は任意のタイミングでオンにしたい。USB-C の有線でも、MIDI キーボードから鳴らしたい。BLE と有線を、任意のタイミングで切り替えたい。

### 9.1 モード
| モード | BLE スタック | リンク | ライトスリープ |
|--------|--------------|--------|----------------|
| **OFF**(**毎回の起動時の既定**) | 完全に停止(メモリを解放) | 何も送らず、何も監視しない | **純正と同じく入る** |
| **BLE** | 動作(広告して接続を待つ) | 自動(ROM がキーボード画面のときだけ送る) | 入らない |
| **USB** | 停止 | 同上 | 入らない |

- 切り替え: **Chromatic の MENU ボタンのメニュー → System タブ → MIDI MODE**(A = 次、B = 前)。または、コンソールの `mode off|ble|usb`。
- **起動から約 20 秒は、どのモードでもスリープしない**(Mac の中継がポートを開く = ESP32 が 1 回再起動し、コンソールで `mode usb` を送る時間のため)。
- OFF のとき、ESP32 は、純正のライトスリープに戻る(操作がなく、FPGA からの通信がなければ)。**MENU ボタンを押すと、FPGA が起こす**ので、スリープ中でも、メニューは操作できる。
- BLE の停止は、`nimble_port_stop()` と `nimble_port_deinit()` で、コントローラも止める(ライトスリープには、これが要る)。切り替えは、専用のタスク(スタック 6 KB)で行い、メニューの描画タスクを止めない。
- 純正のコードへの変更は、**追加だけ**: メニュー(`osd_default.c` に 1 項目)、電源管理(`pwrmgr.c` のライトスリープの条件)。`-Os`・受信タスクの修正(パッチ 0007)は、前のとおり。

### 9.2 有線(USB): Mac の中継プログラム
**Chromatic の USB-C に、MIDI キーボードを直接つなぐことはできない**(USB-C は FPGA のシリアルで、Mac からはシリアルポートにしか見えない。ESP32 も USB を持たない)。Mac を中継にする。

```
MIDI キーボード →(USB)→ Mac →(tools/chromasynth_usb_bridge.swift)→ USB-C のシリアル → ESP32(`m 90 3c 64`)→ ROM
```
- `swiftc -O tools/chromasynth_usb_bridge.swift -o chromasynth_usb_bridge` で作る(追加のインストールは要らない)。`--list`、`--input <名前の一部>`、`--port`、`--dry-run`、`--selftest`。
- 起動すると、シリアルを開き(ESP32 が 1 回再起動)、5 秒待ってから `mode usb` を送る。Ctrl-C で `mode off` を送る(ESP32 がスリープに戻れる)。
- 全ての MIDI 入力(IAC と ChromaSynth 自身を除く)を聴き、ノート(80/90、CC120/123)だけを `m <status> <d1> <d2>` で送る。あとから挿した MIDI キーボードも、2 秒ごとに探して、つなぐ。
- ESP32 のコンソールの `m` は、**何も出力しない**軽い入口で、BLE と同じ `chl_midi_action` を通る。OFF のときは受け付けない。
- 遅延: 音の出る時間の大半は、ROM へのシンボルの送信(約 150 ms)で、BLE と同じ。BLE の接続間隔とばらつき(約 15〜30 ms)が、なくなる分だけ、少し短く、安定する見込み(未測定)。
- テスト: MIDI バイト → コンソールの行の変換は、`make check-usb-bridge`(11 項目。**テストで、メッセージの途中に挟まるリアルタイムバイトを落とす不具合を見つけて直した**)。本物のハードでは未確認。

### 9.3 空きと影響
- アプリ枠の空き: v8 の 12,672 B → **9,696 B**(メニューとモードの管理で約 3 KB)。さらに足すときは、フォントの縮小などで空きを作る。
- 警告なし。`CHLINK_BLE=0` のビルド(`-Os` だけ)も、同じソースで通る(BLE の部分は空)。
- 実機で確認すること(書き込みのあと): (1) 起動時は OFF、(2) 純正のメニューの動作が変わらない(MIDI MODE の項目が System タブにあるだけ)、(3) BLE にすると広告が出て、Mac で接続でき、弾ける、(4) OFF に戻すと、BLE が消え、**コンソールが応答しなくなる(= ライトスリープに入った)**、(5) USB にして、Mac の中継で弾ける、(6) 切り替えを繰り返して、`heap` の空きが減り続けないこと(BLE の停止と再開で、メモリが漏れていないこと)。
