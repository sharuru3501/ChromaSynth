# Chromatic の MCU(ESP32)に書き込むときの安全手順

**§1(確認)・§2(バックアップ)・§3(テーブルの確認)は 2026-11-06 に実行済み。§4 以降はまだ実行していない計画。** 書き込みは、人間(あなた)の操作で行う。Claude は手順を案内し、読み取り専用の確認とビルドまでを担当する。

## 0. 対象
| 項目 | 値 | 出典 |
|------|----|------|
| 本体の版(あなたの個体) | MCU **v0.13.8**、FPGA **v18.14**、ファームウェア **v4.6** | 2026-11-06 にユーザーが報告 |
| 公開ソース | [ModRetro/oss-chromatic-console-mcu](https://github.com/ModRetro/oss-chromatic-console-mcu) の `v4.6`(アプリ版 0.13.8、ESP-IDF 5.3.0)、[chromatic_fpga](https://github.com/ModRetro/chromatic_fpga) の `v18.14` | 取得して確認済み(HEAD が "Publish v4.6" / "Publish v18.14"、設定値と一致) |
| チップ | ESP32(クラシック、4MB フラッシュ、PSRAM なし) | `sdkconfig.defaults`(`FLASHSIZE_4MB`)。型番(MINI-1 / U4WDH)は資料で食い違う |

**触らないもの**: FPGA(ビットストリーム)、ブートローダ(`0x1000`)、パーティションテーブル(`0x8000`)、カートリッジ。アプリ領域だけを書く。FPGA を壊さない限り、USB 経由の書き込み経路は残る。

## 1. 読み取り専用の確認(何も書かない)
本体を **電源オン**にして、USB データケーブルで Mac に繋ぐ(充電専用ケーブルではシリアルが出ない)。ESP-IDF の環境(`. ~/esp/esp-idf/export.sh`)に入っている `esptool.py` を使う。
```bash
ls /dev/cu.usbmodem*                                     # 本体のポート名を確認
esptool.py --port <ポート> --baud 115200 chip_id         # チップの種類
esptool.py --port <ポート> --baud 115200 flash_id        # フラッシュのサイズ(4MB のはず)
espefuse.py --port <ポート> --baud 115200 summary        # eFuse の一覧(読むだけ)
```
- **`espefuse.py` は `summary` 以外のサブコマンド(`burn_*` など)を絶対に実行しない。** eFuse は一度書くと戻せない。
- 見るもの: **フラッシュ暗号化**(`FLASH_CRYPT_CNT` が 0 以外ならオン)と**セキュアブート**(`ABS_DONE_0` が `True` ならオン)。どちらかがオンなら、改造したファームウェアは起動しない(書き込むと文鎮になりうる)。**その場合はここで中止する。**
- esptool が接続すると、本体は一度リセットされる(DTR/RTS で ESP32 の EN と BOOT を操作する)。終わったら再起動して通常画面に戻る。

### 1.1 実行結果(2026-11-06、ユーザーの個体、読み取りのみ)
| 項目 | 結果 |
|------|------|
| ポート | `/dev/cu.usbmodem*`(USB: `Chromatic - Player 01`、VID 0x374E / PID 0x0101、ModRetro)。同じ USB デバイスに `GWU2X`(FPGA のプログラミング用ケーブルとして現れる)も見える。**これには触らない** |
| チップ | **ESP32-U4WDH**(リビジョン v3.1、内蔵フラッシュ、デュアルコア 240MHz、WiFi/BT)。水晶 40MHz |
| 接続 | **115200 bps で接続できた**。stub のアップロードも成功し、終了時に RTS で本体が再起動した(DTR/RTS による自動リセットは動く) |
| フラッシュ | **4MB**、3.3V |
| フラッシュ暗号化 | **オフ**(`FLASH_CRYPT_CNT` = 0) |
| セキュアブート | **オフ**(`ABS_DONE_0` / `ABS_DONE_1` とも False) |
| UART ダウンロード | **有効**(`UART_DOWNLOAD_DIS` = False)。アプリが壊れても書き直せる前提が成り立つ |
| JTAG | 有効(`JTAG_DISABLE` = False) |

→ **改造したファームウェアを書いても起動を拒否される要因(署名検査・暗号化)はない。** 書き込み経路(115200 bps)も、この個体で動くことを確認できた。次は §2 のバックアップ。

## 2. フルバックアップ(4MB)
```bash
esptool.py --port <ポート> --baud 115200 read_flash 0x0 0x400000 backup_A.bin
esptool.py --port <ポート> --baud 115200 read_flash 0x0 0x400000 backup_B.bin
shasum -a 256 backup_A.bin backup_B.bin                  # 2 つが同じであること
```
- 115200 bps で 4MB は **約 6 分**かかる。USB 給電を保ち、途中で抜かない。
- 2 回取って**ハッシュが一致する**ことを確かめる(読み出しの化けを防ぐ)。2 つを別の場所(Mac と別のディスクやクラウド)に保存する。**Wi-Fi の資格情報が含まれることがあるので公開しない**(KortaMod の注意)。
- バックアップは**この個体専用**。別の個体に書き戻さない。

### 2.1 実行結果(2026-11-06)
- 4MB を **2 回**読み、**SHA-256 が一致**した(`448c6267…83b8`)。1 回あたり約 377 秒(88.9 kbit/s)。
- 保存先: `~/Documents/ChromaticBackup/mcu_flash_20261106-152839_{A,B}.bin`(git の管理外、権限 700)。**この 2 つを別のディスクにもコピーしておくこと**(Mac の SSD が壊れたら失われる)。
- 読み出し中に本体は動いていたが、書き込みはしていない。

## 3. バックアップからの確認(書き込む前の机上作業)
- `backup_A.bin` の `0x8000`〜`0x8C00` がパーティションテーブル。ESP-IDF の `gen_esp32part.py` で読める。見るもの: 純正アプリの枠(`factory` か `ota_0`/`ota_1`)の位置と大きさ、`otadata` の有無、NVS の位置。
- **この結果を見てから、書き込み先を決める**(私は今の時点で純正の配置を知らない)。方針:
  1. 純正のアプリの枠には書かず、**別の枠**(ota の空き枠)に書いて、起動の切り替え(`otadata`)だけを変える。元に戻すのは `otadata` を消す/戻すだけ。
  2. 空き枠がなければ、純正の枠に書く。その場合は**バックアップからの復元手順のリハーサルが必須**。
- 試験ファームウェアの大きさが、書き込み先の枠(純正は約 1MB)に収まること。BLE を含む版は枠に収まらない(chromatic-recon は 3MB 枠に区切り直している)。**パーティションテーブルの変更は別の段階として、あらためて確認を取る。**

### 3.1 バックアップから読んだ結果
```
nvs       data nvs     0x009000   24K
phy_init  data phy     0x00f000    4K
factory   app  factory 0x010000    1M
```
- **アプリの枠は `factory` の 1 つだけ**(1MB)。`otadata` も OTA の枠もない。0x110000 以降の約 3MB は**全部 0xFF の未使用領域**。
- 純正のアプリは **762 KB**(枠の 74%)。残り約 262 KB。アプリ記述子: 版 `0.13.8`、プロジェクト `mcu_fw`、ビルド日 2026-09-29、ESP-IDF `v5.3`。公開ソース v4.6 の設定と一致する。
- ブートローダは約 30 KB(0x1000〜)。ここは書き換えない。
- **結論**:
  1. 「別の枠に書いて切り替える」は、今のパーティションテーブルではできない(OTA の枠がない)。
  2. **第 1 段階(BLE なしの試験版)**: 262 KB の余裕があるので、`factory` の枠に書く。戻すのは `factory` の枠だけをバックアップから書き戻す(約 1MB、115200 bps で約 1.5 分)。パーティションテーブルは触らない。
  3. **第 2 段階(BLE)**: BLE のスタックは 262 KB には収まらないので、パーティションテーブルに OTA の枠(未使用の 3MB を使う)を足す必要がある。**この変更は別途確認を取る。** 純正の `factory` は残せるので、`otadata` を消せば純正に戻る構成にできる。

## 4. 復元のリハーサル
**新しいものを書く前に**、手順が動くことを確かめる。バックアップから**アプリ領域だけ**を書き戻す(中身は同じなので、挙動は変わらない)。
```bash
esptool.py --port <ポート> --baud 115200 write_flash --verify <アプリのオフセット> <backup から切り出したアプリ>
```
- 切り出しは `dd`(`bs=1 skip=<オフセット> count=<サイズ>`)。オフセットとサイズは §3 の結果から決める。
- リハーサルで本体が正常に起動することを確認してから、次に進む。

### 4.1 リハーサルの結果(2026-11-06)
- バックアップ A からアプリ領域(`0x10000`、1MB)を切り出し(SHA-256 `0c8980a3…9d09`)、115200 bps で書き込んだ。圧縮後 313,619 B、**28.2 秒**。esptool の MD5 検証(`Hash of data verified`)に合格。
- 書いた後に先頭 `0x0〜0x110000`(ブートローダ、パーティションテーブル、NVS、アプリ)を読み返し(100.7 秒)、**バックアップとバイト単位で完全に一致**した。ブートローダ・テーブル・NVS は書いていないので、書き込みが他の領域に影響していないことも確認できた。
- **書き込みと読み戻しの手順は、この個体で動く。** 復元に必要な時間は約 30 秒(書き込み)。
- 本体の画面と動作の確認(メニュー、ボタン)は、ユーザーの目視による(未記入)。

### 4.2 実際に起きたこと(2026-11-06)
リハーサルの後、ユーザーの LSDJ で、いくつかの曲ファイルの読み込みが FAIL になった。ユーザーの推測では「LSDJ を起動したまま作業したため」。**確認はできていないが、もっともらしい**: esptool は接続のたびに DTR/RTS で ESP32 をリセットするので、ゲームがカートリッジの SRAM に書いている最中に重なると、セーブが壊れる可能性がある(FPGA とカートリッジは動き続けるため、確率は低いと考えていたが、ゼロではなかった)。MCU のフラッシュと LSDJ の曲データ(カートリッジの SRAM)は別のメモリで、今回の作業では SRAM を読み書きしていない。
- **以後の作業の前に、ゲームを終了し、できればカートリッジを抜いておく**(電源を切ってから抜く。電源が入った状態で抜かない)。カートリッジを抜いた状態でメニューが出るかは未確認。出ない場合は、ゲームを起動せずにメニューにいる状態で作業する。
- カートリッジの曲データのバックアップは別の話(必要なら、MR Updater のセーブのバックアップ機能を使う)。

## 5. 書き込み(試験ファームウェア)
1. **ビルド**: ModRetro の公開ソース `v4.6` に、通信機能だけを足す。**ESP-IDF 5.3.0 でビルドする**(ソースの設定がそれ。手元の v5.5.6 ではなく、v5.3.x を別に入れる。約 6GB)。`sdkconfig.defaults` は純正のものを使う(LVGL、フォント、`FLASHSIZE_4MB` など)。
2. **確認**: `esptool.py image_info <bin>` でヘッダとチェックサムを確認。サイズが枠に収まることを確認。
3. **書き込み**: `write_flash --verify`(書いた内容を読み返して一致を確認)。ボーレートは 115200。
4. **起動確認**: 画面が出る、ボタンが効く、メニューが開く、バッテリー表示が出る。1 つでも変なら、すぐ元に戻す(§6)。
- 書き込み中は USB 給電を保ち、抜かない。バッテリーを十分に充電しておく。
- **安全モード**: 起動時にあるボタン(例: MENU)を押していたら、追加機能を動かさず純正と同じ動作にする。

### 5.1 純正ソース(v4.6)を改造せずにビルドした結果(2026-11-06、まだ書き込んでいない)
- ESP-IDF **v5.3**(`~/esp/esp-idf-v5.3`)で `idf.py build`(ESP-IDF v5.5.6 の `~/esp/esp-idf` とは別。コンポーネントは `dependencies.lock` で固定)。**警告なしでビルド成功**。
- **サイズが純正とバイト単位で同じ**: アプリ 781,168 B(純正の使用範囲と一致)、ブートローダ 26,752 B、パーティションテーブル 3,072 B。**パーティションテーブルはバイト単位で完全に一致**。アプリ記述子は版 `0.13.8`・プロジェクト `mcu_fw`・IDF `v5.3` で一致(ビルド時刻だけ違う)。
- **ビット単位では一致しない**: アプリで約 76,000 B(約 10%)、ブートローダで 44 B が違う。確認できた違いの原因は、①ビルド時刻、②**ツールチェーンの違い**(私の Mac 用ツールチェーンの newlib に `HOST-x86_64-apple-darwin21.1/` という文字列が入るが、純正にはない。純正は別のホストでビルドされている)。コードの機能が同じかどうかは、ビット比較では証明できない。
- **したがって次の段階として、改造前のビルドそのものを一度書いて、純正と同じに動くことを確認する**(§4 のリハーサルの後)。それが通れば、改造後に問題が出たとき、原因を追加した部分に絞れる。
- 生成物: `.../scratchpad/ext/mcu/build/mcu_fw.bin`(スクラッチパッドにあり、リポジトリには入れない)。

### 5.2 改造前のビルドを書いた結果(2026-11-06)
- **接続の落とし穴**: 1 回目は「No serial data received」で接続できなかった(書き込みの前に止まったので、何も書かれていない)。**本体を電源 OFF、USB を抜いて 10 秒待ち、カートリッジを挿して USB を繋いでから電源 ON** にしたら繋がった。それ以前の「カートなしでメニューが固まる」状態では繋がらなかった。**USB の橋渡しは FPGA が担当しており、FPGA が正常に動いている(カートが入って本体が通常状態)ことが条件らしい**(原因は未確認)。繋がらないときは、完全な電源入れ直しをまず試す。
- 書き込み: ガード確認(サイズ 781,168 B、版 0.13.8、プロジェクト `mcu_fw`)→ `0x10000` に **27.6 秒**で書き込み、MD5 検証に合格。
- 読み戻し: アプリ領域は**ビルドしたファイルと完全に一致**、先頭 `0x0〜0x10000`(ブートローダ・テーブル・NVS)は**バックアップと完全に一致**。
- **本体の動作確認(ユーザーの目視): 起動する、テトリスが遊べる、メニューからの MCU / FPGA / FW の版表示も変わらない。** 純正ソースのビルドが、実機で純正と同じに動くことを確認できた。

### 5.3 試験ファームウェア v0 を書いた結果と、USB シリアルの性質(2026-11-06)
- v0 を `0x10000` に **27.6 秒**で書き込み、MD5 検証に合格。読み戻しで**アプリ領域はビルドと完全に一致**。先頭 64KB のうち、ブートローダ・パーティションテーブル・phy_init は**バックアップと完全に一致**、**NVS だけ 99 バイト違った**(`0x9024`〜`0x9398`)。私の書き込みは `0x10000` 以降だけなので、本体が動作中に書く設定領域の更新と考えている(前回の確認と今回の間に本体を使っている)。**以後の「先頭の一致確認」は NVS(`0x9000`〜`0xF000`)を除いて行う。**
- v0 は**起動する**: USB のコンソールに ESP-IDF のブートログと `mcu>` のプロンプトが出る(純正はコンソールが GPIO 35/36 向きで USB には出ない)。ポートを開いて 45 秒聞き続けても、再起動の繰り返しや異常はない。
- **USB シリアルの DTR/RTS は ESP32 のリセットに直結している**(FPGA の `top.v`): `EN = ~RTS`(RTS オンの間 ESP32 はリセットされたまま)、`IO0` は DTR/RTS のどちらかがオンなら Low(次のリセットでダウンロードモード)。Mac でポートを開くと既定で両方オンになるので、**ポートを開く前に DTR=False、RTS=False にする**(pyserial なら `s.dtr=False; s.rts=False` を `open()` の前に)。それでも、開いた瞬間に 1 回リセットが入る(起動ログが先頭から出る)。
- **コンソールの入力(Mac → ESP32)は、今のところ届いていない**: CR / LF / CRLF、DTR オンなど試したが、`chver` や `help` に反応しない。**原因は未確認**(ESP-IDF の REPL 設定は正常、FPGA の配線にも入力を止める記述は見つからなかった)。出力(ESP32 → Mac)は確実に動く。
- → **入力に頼らず、本体が自分で試験を行って結果を出力する v1**(パッチ 0002)を作った(未書き込み)。

### 5.4 v1(自己試験版)を書いた結果(2026-11-06)
- ガード(SHA-256 `e11b3897…`、782,944 B、版 0.13.8)→ `0x10000` に **27.7 秒**で書き込み、MD5 検証に合格。読み戻しで**アプリ領域はビルドと完全に一致**、**ブートローダ・パーティションテーブル・phy_init はバックアップと完全に一致**(NVS は除外して照合)。
- 試験の実行(`gpd` 5 回 → 仮想 START → `gpd` 5 回)は、ポートを開いて ESP32 を起動し直した 6 秒後から。結果は下に追記する。

### 5.5 v1 の自己試験の結果と v2(2026-11-06)
- v1 を書いた後、ポートを開いて(ESP32 が再起動して)42 秒聞いた。**起動ログと `mcu>` は出たが、自己試験の出力は 1 行も出なかった**(「selftest start」すら出ない)。ユーザーの目視でも、テトリスの PAUSE 画面は変化なし(仮想 START は送られていない)。
- 原因の仮説(**未確認**): 純正のタスクの優先度は FPGA 通信 15・電源管理 16、**コンソール(REPL)は既定の 2、私の試験タスクは 3**。優先度の高いタスクが CPU を使い続けているなら、低いタスクは動けない。コンソールが `mcu>` を 1 回出したあと入力に反応しないことも説明できる。もう 1 つの可能性: `printf` が flush されていない(行バッファの問題)。
- v2(パッチ 0003): 試験タスクを優先度 18、コンソールを 17 にする。出力を標準出力と **ROM の直接出力(`esp_rom_printf`)**の両方に出す。タスク開始直後に「selftest task started」を出す(タスクが動いているかを見分けるため)。
- v2 のイメージ: 783,488 B、ヘッダ・チェックサム・ハッシュは有効。まだ書き込んでいない。

### 5.6 v2 の結果と v3(2026-11-06)
- v2 を書き込み(27.7 秒、MD5 検証合格、アプリ領域は読み戻しで一致、ブートローダ・テーブル・phy_init はバックアップと一致)。ポートを開いて 40 秒聞いた結果: **「selftest task started」は出た(タスクは動く)が、その 6 秒後の出力も、コンソール入力への反応も出ない**。ユーザーの目視でも、テトリスの PAUSE 画面は変化なし。
- **原因(ソースで確認)**: 純正の電源管理 `pwrmgr.c` が、操作がない状態が 100 ms 続くと `esp_light_sleep_start()` で **ライトスリープ(CPU 停止)**に入る。起きるのは FPGA からの UART メッセージ(GPIO10 が Low)のときだけ。眠っている間は、タイマー・タスク・コンソール入力がすべて止まる。起動の約 2 秒後(`PwrMgr_Task` の開始後)に眠るので、v1・v2 の試験もコンソールも止まっていた。**これは「本体内蔵 ESP32 でゲーム中に通信する」設計全体に効く**(MCU が眠っていると、`gpd` を読むことも仮想ボタンを送ることもできない)。
- v3(パッチ 0004): `PwrMgr_TriggerLightSleep()` を何もしない関数にする(呼び出し元は `IdleTimerCB` だけ)。**電池の持ちが悪くなる**(通信を使う間だけ眠らせない、という切り替えは後で入れる)。
- v3 のイメージ: 783,456 B、ヘッダ・チェックサム・ハッシュは有効。まだ書き込んでいない。

### 5.7 v3 の結果(2026-11-06)
- v3 を書き込み(27.7 秒、MD5 検証合格、アプリ領域は読み戻しで一致、ブートローダ・テーブル・phy_init はバックアップと一致)。
- **自己試験が最後まで実行された**: 起動の約 7 秒後に開始 → `T1`(`gpd` 5 回)→ `T2`(仮想 START 150 ms)→ `T3`(`gpd` 5 回)→ 3 秒ごとの `HB`。**ESP32 は眠らずに動き続けた**。書き込み直後に、ポートを開く前の無人の状態でも試験が走っていた(出力が残っていた)。
- **`gpd` はテトリス実行中に毎回 `61 51 30 A8 35 09 41 4B`**(10 回連続 + 定期読み出しで一致)。並び: 受信バイト `[0..3]` = `obpd[13],[12],[11],[10]`、`[4..7]` = `bgpd[5],[4],[3],[2]`。OBJ パレット1の色1 = `0x30A8`・色2 = `0x6151`、BG パレット0の色1 = `0x414B`・色2 = `0x3509`(どれも RGB555 として妥当。テトリスはパレットを書かないので、Chromatic の自動配色)。**設計(CHROMATIC_LINK.md §2)の想定した並びと一致**。
- **確認できたこと**: 上りの経路の MCU 側(要求 → 8 バイトの受信)が実機で動く。**未確認**: ROM が書いた値が `gpd` に反映されるか(ChromaSynth の ROM が必要)、仮想 START がゲームに届くか(ユーザーの目視待ち)。

## 6. 元に戻す
- 起動はするが変なとき: 本体を USB で繋ぎ、バックアップのアプリ領域を書き戻す(§4 と同じコマンド)。または、起動の切り替えを戻す。
- 起動しないとき: `esptool.py` で `write_flash` する(ESP32 の ROM ブートローダは、アプリが壊れていても DTR/RTS でダウンロードモードに入れる)。それでも本体を認識しないときは、ModRetro の **MR Updater**(公式)で純正の MCU ファームウェアに戻す。
- **FPGA 側が生きていることが前提**。FPGA を触らないのはこのため。

## 7. 残るリスク(正直に)
- 「USB-C → FPGA → ESP32 の UART」と DTR/RTS による自動ダウンロードモードは、二次情報(他人のファームウェアの README)による。**あなたの個体で動くことは、§1 で初めて確認できる。**
- 純正のアプリが `factory` 枠のみで、空き枠がない場合、リハーサルでも元の動作に戻せることしか確認できない(失敗した状態の復旧は、ROM ブートローダ経由に頼る)。
- ESP32 のフラッシュ書き込みは電源の瞬断に弱い(書き込み中に落ちると、その領域が壊れる。ブートローダとパーティションテーブルを触らなければ、再度書き込める)。
- 純正の更新ツールが、改造版が入った状態の本体を認識しない可能性がある(公式の記事にも「検出できない場合がある」とある)。
- ModRetro が将来ファームウェアを更新すると、MCU と FPGA の通信プロトコル(V1/V2)が変わる可能性がある。この手順は v4.6 / v18.14 専用。
