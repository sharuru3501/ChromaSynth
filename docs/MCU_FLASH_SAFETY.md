## 0. 対象
| 項目 | 値 | 出典 |
|------|----|------|
| 本体の版(あなたの個体) | MCU **v0.13.8**、FPGA **v18.14**、ファームウェア **v4.6** | 2026-11-06 にユーザーが報告 |
| 公開ソース | [ModRetro/oss-chromatic-console-mcu](https://github.com/ModRetro/oss-chromatic-console-mcu) の `v4.6`(アプリ版 0.13.8、ESP-IDF 5.3.0)、[chromatic_fpga](https://github.com/ModRetro/chromatic_fpga) の `v18.14` | 取得して確認済み(HEAD が "Publish v4.6" / "Publish v18.14"、設定値と一致) |
| チップ | ESP32(クラシック、4MB フラッシュ、PSRAM なし) | `sdkconfig.defaults`(`FLASHSIZE_4MB`)。型番(MINI-1 / U4WDH)は資料で食い違う |
| 書き込みの経路 | USB-C → FPGA の USB 複合デバイス(CDC シリアル) → ESP32 の UART0。**115200 bps 固定**(460800 は接続が切れる報告) | chromatic-recon / chromatic-grok の README(二次情報) |

**触らないもの**: FPGA(ビットストリーム)、ブートローダ(`0x1000`)、パーティションテーブル(`0x8000`)、カートリッジ。アプリ領域だけを書く。FPGA を壊さない限り、USB 経由の書き込み経路は残る。

## 1. 読み取り専用の確認(何も書かない)
本体を **電源オン**にして、USB データケーブルで Mac に繋ぐ(充電専用ケーブルではシリアルが出ない)。ESP-IDF の環境(`. ~/esp/esp-idf/export.sh`)に入っている `esptool.py` を使う。
```bash
ls /dev/cu.usbmodem*                                     # 本体のポート名を確認
esptool.py --port <ポート> --baud 115200 chip_id         # チップの種類
esptool.py --port <ポート> --baud 115200 flash_id        # フラッシュのサイズ(4MB のはず)
espefuse.py --port <ポート> --baud 115200 summary        # eFuse の一覧(読むだけ)
```
- **`espefuse.py` は `summary` 以外のサブコマンド(`burn_*` など)を絶対に実行しない。** eFuse は一度書くと戻せない。
- 見るもの: **フラッシュ暗号化**(`FLASH_CRYPT_CNT` が 0 以外ならオン)と**セキュアブート**(`ABS_DONE_0` が `True` ならオン)。どちらかがオンなら、改造したファームウェアは起動しない(書き込むと文鎮になりうる)。**その場合はここで中止する。**
- esptool が接続すると、本体は一度リセットされる(DTR/RTS で ESP32 の EN と BOOT を操作する)。終わったら再起動して通常画面に戻る。

§1.1(実行結果)は [log/MCU_FLASH_SAFETY_LOG.md](log/MCU_FLASH_SAFETY_LOG.md)。

## 2. フルバックアップ(4MB)
```bash
esptool.py --port <ポート> --baud 115200 read_flash 0x0 0x400000 backup_A.bin
esptool.py --port <ポート> --baud 115200 read_flash 0x0 0x400000 backup_B.bin
shasum -a 256 backup_A.bin backup_B.bin                  # 2 つが同じであること
```
- 115200 bps で 4MB は **約 6 分**かかる。USB 給電を保ち、途中で抜かない。
- 2 回取って**ハッシュが一致する**ことを確かめる(読み出しの化けを防ぐ)。2 つを別の場所(Mac と別のディスクやクラウド)に保存する。**Wi-Fi の資格情報が含まれることがあるので公開しない**(KortaMod の注意)。
- バックアップは**この個体専用**。別の個体に書き戻さない。

§2.1(実行結果)は [log/MCU_FLASH_SAFETY_LOG.md](log/MCU_FLASH_SAFETY_LOG.md)。

## 3. バックアップからの確認(書き込む前の机上作業)
- `backup_A.bin` の `0x8000`〜`0x8C00` がパーティションテーブル。ESP-IDF の `gen_esp32part.py` で読める。見るもの: 純正アプリの枠(`factory` か `ota_0`/`ota_1`)の位置と大きさ、`otadata` の有無、NVS の位置。
- **この結果を見てから、書き込み先を決める**(私は今の時点で純正の配置を知らない)。方針:
  1. 純正のアプリの枠には書かず、**別の枠**(ota の空き枠)に書いて、起動の切り替え(`otadata`)だけを変える。元に戻すのは `otadata` を消す/戻すだけ。
  2. 空き枠がなければ、純正の枠に書く。その場合は**バックアップからの復元手順のリハーサルが必須**。
- 試験ファームウェアの大きさが、書き込み先の枠(純正は約 1MB)に収まること。BLE を含む版は枠に収まらない(chromatic-recon は 3MB 枠に区切り直している)。**パーティションテーブルの変更は別の段階として、あらためて確認を取る。**

§3.1(バックアップから読んだ結果)は [log/MCU_FLASH_SAFETY_LOG.md](log/MCU_FLASH_SAFETY_LOG.md)。

## 4. 復元のリハーサル
**新しいものを書く前に**、手順が動くことを確かめる。バックアップから**アプリ領域だけ**を書き戻す(中身は同じなので、挙動は変わらない)。
```bash
esptool.py --port <ポート> --baud 115200 write_flash --verify <アプリのオフセット> <backup から切り出したアプリ>
```
- 切り出しは `dd`(`bs=1 skip=<オフセット> count=<サイズ>`)。オフセットとサイズは §3 の結果から決める。
- リハーサルで本体が正常に起動することを確認してから、次に進む。

§4.1〜4.2(リハーサルの結果、実際に起きたこと)は [log/MCU_FLASH_SAFETY_LOG.md](log/MCU_FLASH_SAFETY_LOG.md)。

## 5. 書き込み(試験ファームウェア)
1. **ビルド**: ModRetro の公開ソース `v4.6` に、通信機能だけを足す。**ESP-IDF 5.3.0 でビルドする**(ソースの設定がそれ。手元の v5.5.6 ではなく、v5.3.x を別に入れる。約 6GB)。`sdkconfig.defaults` は純正のものを使う(LVGL、フォント、`FLASHSIZE_4MB` など)。
2. **確認**: `esptool.py image_info <bin>` でヘッダとチェックサムを確認。サイズが枠に収まることを確認。
3. **書き込み**: `write_flash --verify`(書いた内容を読み返して一致を確認)。ボーレートは 115200。
4. **起動確認**: 画面が出る、ボタンが効く、メニューが開く、バッテリー表示が出る。1 つでも変なら、すぐ元に戻す(§6)。
- 書き込み中は USB 給電を保ち、抜かない。バッテリーを十分に充電しておく。
- **安全モード**: 起動時にあるボタン(例: MENU)を押していたら、追加機能を動かさず純正と同じ動作にする。

§5.1〜5.15(各版のビルドと書き込みの記録。最新は §5.15)は [log/MCU_FLASH_SAFETY_LOG.md](log/MCU_FLASH_SAFETY_LOG.md)。

## 6. 元に戻す
- 起動はするが変なとき: 本体を USB で繋ぎ、バックアップのアプリ領域を書き戻す(§4 と同じコマンド)。または、起動の切り替えを戻す。
- 起動しないとき: `esptool.py` で `write_flash` する(ESP32 の ROM ブートローダは、アプリが壊れていても DTR/RTS でダウンロードモードに入れる)。それでも本体を認識しないときは、ModRetro の **MR Updater**(公式)で純正の MCU ファームウェアに戻す。
- **FPGA 側が生きていることが前提**。FPGA を触らないのはこのため。

## 7. 残るリスク(正直に)
- 「USB-C → FPGA → ESP32 の UART」と DTR/RTS による自動ダウンロードモードは、二次情報(他人のファームウェアの README)による。**あなたの個体で動くことは、§1 で初めて確認できる。**
- 純正のアプリが `factory` 枠のみで、空き枠がない場合、リハーサルでも元の動作に戻せることしか確認できない(失敗した状態の復旧は、ROM ブートローダ経由に頼る)。
- ESP32 のフラッシュ書き込みは電源の瞬断に弱い(書き込み中に落ちると、その領域が壊れる。ブートローダとパーティションテーブルを触らなければ、再度書き込める)。
- 純正の更新ツールが、改造版が入った状態の本体を認識しない可能性がある(公式の記事にも「検出できない場合がある」とある)。
- ModRetro が将来ファームウェアを更新すると、MCU と FPGA の通信プロトコル(V1/V2)が変わる可能性がある。この手順は v4.6 / v18.14 専用。
