# ブリッジ設計(M6): MIDI ⇄ リンクケーブル

ChromaSynth ROM は MIDI を**リンクポート**で受け渡す。カートリッジのコードは Bluetooth も USB も使えないので、
間に**ブリッジ**(小さなマイコン基板)を挟み、USB-MIDI / DIN-5 / BLE MIDI とリンクケーブルを相互に変換する。

```
 [DAW / Mac]──USB-MIDI──┐
 [キーボード]─DIN-5─────┤                      リンクケーブル
 [BLE MIDI機器]─BLE─────┼─► ブリッジ(ESP32-S3) ◄──(SC, SI, SO, GND)──► Chromatic(ChromaSynth ROM)
 [DAW]◄─BLE MIDI────────┘   クロックのマスター                          スレーブ(外部クロック)
```

- **ブリッジ = リンクのクロックのマスター、GB = スレーブ**。GB は SC=$80(外部クロック)で待ち受ける。
- ROM 側は実装済み・テスト済み。ブリッジ側は**仕様、参照実装(`tools/bridge_ref.py`)、C の中核とファームウェアのソース**(`firmware/`、[FIRMWARE.md](FIRMWARE.md))まで。ESP-IDF でのビルドと基板は未着手。
- 状態: **実機・ブリッジでは一度も動かしていない**。ROM 側と参照実装の整合は、PyBoy 上で確認した(`tools/headless_midi_test.py`)。

## 2. リンクプロトコル

GB のシリアルは SPI モード 3 相当(アイドル時クロック High、立ち上がりで取り込み、MSB から)。
ブリッジ側は SPI マスターペリフェラル(MISO←SO、MOSI→SI、SCK→SC)で駆動できる。

### 転送の仕組み
- 1回の転送 = 1バイトを同時に送受信。**ブリッジが送ったバイトが GB に届き、同時に GB が前回の転送後に用意しておいたバイトが返る**(返信は1転送ぶん遅れる)。
- GB 側は、転送完了割り込み(Serial)で SB を受け取り、**次の返信を SB に載せ、SC=$80 で再び待ち受ける**。
- **ブリッジは、GB が再び待ち受けるまで次のバイトを始めてはいけない**(Pan Docs: スレーブはマスターが始める前に待ち受けておく必要がある)。ROM の ISR は約 100 サイクル(約 100 µs)なので、**バイト間隔は 250 µs 以上**にする。

### 空きバイト `$FD`
送るものが無いとき、双方向とも `$FD` を使う(MIDI 仕様で未定義のリアルタイムメッセージ。通常の MIDI パーサは無視する)。
- ブリッジ → GB: 送るデータが無くても**一定間隔で `$FD` を送り続ける**(= GB の返信を受け取るためのポーリング)。ROM は `$FD` を受信バッファに入れずに捨てる。
- GB → ブリッジ: 送信キューが空なら `$FD` が返る。
- **`$FF` が返ってきたら「GB が待ち受けていない/ケーブル未接続」**(ROM はデータとして `$FF` を絶対に送らない)。ブリッジは送信を止めてゆっくり再試行する。

### タイミング(既定値)
| 項目 | 値 | 理由 |
|------|----|------|
| SCK | 32 kHz | 1バイト 250 µs。GB のシステムクロック(約 4.19 MHz)に対して十分に低い |
| バイト間隔 | 250 µs | ROM の ISR(約 100 µs)の2.5倍。余裕を持たせた |
| 1バイトあたり | 500 µs → 約 **2000 バイト/秒** | フィルタ後の MIDI には十分(§3 のクロックは 48 バイト/秒) |
| アイドルポーリング | 2 ms ごと | GB からの出力(クロック・ノート)の遅れは最大 2 ms + 1転送 |
| 3音の和音(9バイト) | 約 4.5 ms | |

最大負荷時(2000 バイト/秒)は ISR が CPU の約 2 割を使う。通常運用(ポーリング 500 回/秒 + 少量のデータ)では数 % 。

### GB が理解するメッセージ(ブリッジが転送するもの)
`tools/bridge_ref.py` が実行可能な仕様。**ステータス付きの完全なメッセージだけ**を送る(ランニングステータスは展開する)。

| 方向 | メッセージ | 備考 |
|------|------------|------|
| →GB | ノートオン/オフ(`9n`/`8n`)、ピッチベンド(`En`)、CC1・CC120・CC123 | それ以外(アフタータッチ、プログラムチェンジ、他の CC、SysEx、アクティブセンシング)は**ブリッジが捨てる** |
| →GB | `$F8`(クロック)、`$FA`(スタート)、`$FB`(コンティニュー)、`$FC`(ストップ) | **クロックは1ティック=1バイト(12回/拍)**。ブリッジが DAW の24回/拍を2で割って送る。`$FA` の直後の最初のクロックがティック0 |
| GB→ | `$F8`、`$FA`、`$FB`、`$FC` | GB がマスター(SYNC=OUT)のとき。ブリッジは 12→24 回/拍に補間して DAW へ(§補間) |
| GB→ | ノートオン/オフ(`9n`/`8n`) | シーケンサが鳴らした音。MIDI チャンネルは各 CH の割り当て(0 なら送らない)。ベロシティは固定100 |

### クロックの変換
- **DAW → GB(24→12)**: 受け取ったクロックを1つおきに転送。`$FA` で位相をリセットし、スタート直後の1つ目のクロックを転送する(= ティック0)。`$FB` では位相を保つ。
- **GB → DAW(12→24)**: GB のティックを受け取った時刻 t で `$F8` を出し、**前の間隔の半分後**(t + P/2)にもう1つ出す。P は直前2つのティックの間隔。`$FA`/`$FC` でテンポの基準をリセットする(停止中の長い間隔で補間しない)。0.25 秒より長い間隔も補間しない。
- 1ティック = 1/12 拍。24 ppqn にしなかった理由は、GB 側の192ティックを8ビットに収めて軽くするため([ROLL_DESIGN.md](ROLL_DESIGN.md))。変換はブリッジ側の仕事。

### バッファと保護
- GB の受信リング 256 バイト、送信キュー 255 バイト。**送信キューが満杯のときは新しいバイトを黙って捨てる**(ブリッジが居なくても GB は止まらない)。
- SYNC=OFF(既定)のときは何も送信キューに積まない(ブリッジ無しで使うときに、後から接続したブリッジへ古いデータが流れないように)。

## 3. GB 側の設定(音色編集画面の MIDI ページ、行7 `SYNC`)
| 値 | 動作 |
|----|------|
| 0 OFF | クロックもノートも送らない。受信したリアルタイムも無視(既定) |
| 1 OUT | **GB がマスター**。スタート/ストップ、ティックごとのクロック、シーケンサのノートを送る。受信したリアルタイムは無視 |
| 2 IN | **DAW がマスター**。クロック/スタート/コンティニュー/ストップに従って再生。本体の SELECT+START は無効 |

IN のとき、受信クロックは最大4個まで溜められ、1フレームで最大4ティック進む。それ以上のバーストは捨てる(速すぎる/乱れた入力でも固まらない)。

## 4. ハードウェア

### 配線(標準リンクケーブル、GB 本体側から見た番号)
| ピン | 信号 | ブリッジ側 | 備考 |
|------|------|-----------|------|
| 1 | VCC | **接続しない** | Chromatic の電源は不明。ブリッジは USB から給電する |
| 2 | SO(GB の出力) | MISO(入力) | GB→ブリッジ |
| 3 | SI(GB の入力) | MOSI(出力) | ブリッジ→GB |
| 4 | SD | 接続しない | 未使用 |
| 5 | SC(クロック) | SCK(出力) | ブリッジがマスター |
| 6 | GND | GND | |

### 実測の手順(電圧とピン配置を決める)
1. GBC 用リンクケーブルを用意し、片側を切って端をむき出す(または分解可能なブレイクアウトを使う)。
2. Chromatic の**電源を入れ、ROM を動かした状態**で、テスターの COM を GND(ピン6)に当て、SC・SO・SI の待機電圧を測る。**測るだけで何も接続しない**。
3. 導通を測り、ケーブルの端のピン番号と実際の配線の対応(交差の有無)を確認する。
4. 結果:
   - **約 3.3V** → ブリッジ(3.3V)と**直結**してよい。各信号に 330 Ω の直列抵抗を入れる。
   - **約 5V** → レベル変換が必要:
     - ブリッジ→GB(SC, SI): 5V 電源の **74AHCT125**(入力は TTL レベルなので 3.3V を High と認識する)。
     - GB→ブリッジ(SO): 3.3V 電源の 74LVC 系、または抵抗分圧(例 1.8 kΩ + 3.3 kΩ)。ESP32-S3 の入力は 5V 耐性がない。
   - どちらでもない/不明 → 接続しない。

### MCU の選定
| | ESP32-S3 | RP2040 (Pico) |
|---|----------|---------------|
| USB-MIDI デバイス | ネイティブ USB | ネイティブ USB(TinyUSB) |
| **BLE MIDI** | **内蔵(BLE 5)** | 内蔵なし(Pico W は BLE あり) |
| DIN-5 MIDI IN | UART + フォトカプラ | UART + フォトカプラ |
| リンクの駆動 | SPI マスター(モード3) | PIO またはSPI |
| 3.3V | はい | はい |

**推奨は ESP32-S3**(USB-MIDI、BLE MIDI、DIN-5 が1チップで揃い、1枚の基板で段階的に広げられる)。

### 部品(目安)
ESP32-S3 開発ボード、GBC 用リンクケーブル、74AHCT125(5V だった場合)、抵抗(330 Ω、必要なら分圧用)、
DIN-5 MIDI IN を付けるなら 6N138(または高速フォトカプラ)+ 抵抗 + DIN-5 ソケット、USB-C ケーブル。

## 5. ファームウェアの設計

詳細は [FIRMWARE.md](FIRMWARE.md)。**中核ロジックは `tools/bridge_ref.py` と `firmware/core/bridge_core.c` が同じ動作**(正解トレースで突き合わせ済み)。以下は全体像。

```
入力タスク      USB-MIDI / DIN UART / BLE MIDI のバイト列 → bridge.host_in(bytes)
リンクタスク    ループ:
                  b = to_gb キューから1バイト(無ければ $FD)
                  reply = SPI で b を送り、同時に1バイト受け取る        # SPI モード3, 32 kHz
                  if reply == $FF: link_down(); 待つ; continue         # GB が待ち受けていない
                  bridge.gb_in(reply, now)
                  待つ(バイト間隔 250 µs。キューが空なら 2 ms)
出力タスク      bridge.host_out_due(now) → USB-MIDI / BLE へ送る(補間したクロックは時刻通りに)
```
- SPI の1バイト転送(250 µs)と、バイト間隔のタイマはソフトウェアで管理する(CS は使わない)。
- 起動時、GB から `$FF` 以外が返るまでは何も送らない。
- ESP32 のタイマ精度(数 µs)に対し、250 µs の間隔は十分に余裕がある。
- **BLE MIDI**は2つの役割: ① DAW 向けに BLE MIDI の**ペリフェラル**(macOS は「Audio MIDI 設定 → Bluetooth」から接続)、② BLE キーボード向けに**セントラル**(BLE MIDI サービス UUID `03B80E5A-EDE8-4B33-A751-6CE34EC4C700` を探して接続)。同時動作は ESP32 の NimBLE で可能なはずだが、**M8 で実機確認する**。BLE MIDI のパケットにはタイムスタンプが付くので、入力側で取り除く。
